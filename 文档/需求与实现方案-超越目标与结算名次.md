# 游戏内超越目标卡片与结算名次变化方案

日期：2026-10-20。状态：HUD 已实现；新版结算按最终原型接入独立 Prefab、真实榜单冲榜与彩纸庆祝，后端新增按操作 ID 绑定的结算快照。开发数据库和客户端模拟验证通过，Creator 与微信真机视觉待验收。详见 [新版结算实现验证](新版结算-实现验证.md)。

## 1. 意图与范围

对局 HUD 与新版结算均按已确认原型落地。结算采用独立皇冠荣誉榜单、动态得分、三枚操作按钮、从底部向上的冲榜和彩纸庆祝。排行榜最高分约 58 万为用户提供的现状，生产布局完整支持接口允许的十位数分数。

对局中在右上角展示下一个要超越的人。上方为「得分」与暖黄色实时数字，下方为头像、昵称、奶油白目标数字；无背景签、不常驻显示「即将超越」或分隔圆点，所有文字水平。目标被超越时单独替换下方目标组，上方得分区保持位置、字号和字框稳定。结算的视觉与动作以 [结算冲榜原型](../design/原型-超越目标与结算名次/结算冲榜动画.html) 为准。

两个界面共用同一条数据链路和同一份名次语义：

```text
PlayerSessionStore / PlayerProfileStore → GET /leaderboard/target
                       ↓
OvertakeRivalStore → PlayUIState.overtake → OvertakeTargetWidget

game_finished → /sync.settlement（本局 operationId）
                       ↓
PlayerCloudSyncStore → PlayUIState.settlementRank → GameOverOverlayController
```

### 1.1 已确认的产品规则

| # | 规则 | 来源 |
| --- | --- | --- |
| 1 | 位置在游戏内右上角，但不是贴屏幕角，需要距顶部一段距离并适配异形屏 | 需求 |
| 2 | 卡片显示头像、昵称、分数 | 需求 |
| 3 | 本局开始后，玩家有历史分数时**优先以自己历史最高分为目标**，越过后再显示榜上下一位玩家 | 需求优化，当前精简排版不再依赖状态前缀 |
| 4 | 玩家没有历史分数时，**本局不显示目标区**，得分区常驻；结算排行业务需求保留 | 需求优化 |
| 5 | 结算后显示名次，并播放"上升了多少名"的动画 | 需求优化 |
| 6 | 卡片无点击入口，不显示"还差 N 分" | 需求 |
| 7 | 目标与本局分数使用同一个静态 Prefab（节点、Sprite、Label 在 Creator 内维护） | 本次原型建议 |
| 8 | 允许修改后端 | 需求 |
| 9 | 目标隐藏时仍保留本局分数，且本局分数的位置不跳动；昵称限定最大宽度，超出显示 `...` | 本次请求与原型 |

### 1.2 明确不做

- 不做点击打开排行榜、不做差值进度条。
- 不新增排行榜分页浏览能力，`LeaderboardPopupController` 保持现状。
- 不改变结算弹窗现有分数、最高合成、金币奖励的展示与逻辑。
- 不把名次写进本局存档（`OngoingGameSession`）或云快照。

## 2. 三态卡片与结算名次的状态定义

目标区只有三种可见状态，外加隐藏；以下「隐藏」均只指目标区，本局分数常驻：

| 状态 | 触发条件 | 标题 | 主体 |
| --- | --- | --- | --- |
| `self` | 有历史分数，且 `本局分数 ≤ 历史最高分` | 无常驻状态标题 | 自己的头像 / 昵称 / 历史最高分 |
| `rival` | 本局分数已超过历史最高分，榜上存在 `value ≥ 本局分数` 的玩家（同分仍需超越） | 无常驻状态标题 | 对方头像 / 昵称 / 分数 |
| `top` | 已无更高分玩家（`isTop`） | 已登顶 | 靠右文字，隐藏头像与分数 |
| 隐藏 | 未登录 / 无历史分数 / 接口不可用 / 数据为空 | — | 收起下方目标区，保留上方得分区 |

结算名次区三种情况：

| 条件 | 展示 |
| --- | --- |
| `previous` 与 `current` 都有 | `第 13 名 ↑8` |
| `previous === null`（首次上榜） | `新上榜 第 13 名`，无箭头 |
| `current === null` 或请求失败 | 保留新版基础结算，显示排行未更新状态，不播放冲榜或庆祝 |

## 4. 后端契约

### 4.1 新增接口 `GET /v1/leaderboard/target`

请求：

```http
GET /v1/leaderboard/target?metric=score&value=9200&limit=5
Authorization: Bearer <token>
```

| 参数 | 类型 | 说明 |
| --- | --- | --- |
| `metric` | `score` \| `highestNumber` | 默认 `score`，与现有排行榜一致 |
| `value` | 非负整数 | 比较基线；返回**严格大于**该值的玩家 |
| `limit` | 1..20，默认 5 | 返回条数上限 |

响应：

```json
{
  "data": {
    "entries": [
      {
        "rank": 12,
        "displayName": "小西瓜",
        "value": 9350,
        "avatarIndex": 3,
        "avatarType": "builtin",
        "wechatAvatarUrl": null,
        "isSelf": false
      }
    ],
    "self": {
      "rank": 13,
      "displayName": "我",
      "value": 9200,
      "avatarIndex": 7,
      "avatarType": "wechat",
      "wechatAvatarUrl": "https://...",
      "isSelf": true
    },
    "isTop": false
  }
}
```

实现要点：

1. 复用现有排行榜条目 DTO 与名次计算，避免两套排名口径。
2. 查询条件必须包含 `player_id <> 当前玩家`：客户端本地历史分与榜单 `value` 存在同步延迟时，自己可能落在"严格大于基线"的集合里。
3. 目标按分数升序、内部玩家 ID 升序排列；全局名次按分数降序、内部玩家 ID 升序，与现有榜单一致，不使用容易随同步变化的 `updated_at`。
4. `isTop = entries.length === 0`。
5. 名次口径必须与 `/v1/leaderboard` 的 `self.rank` 完全一致（同一套 tie-break 规则），否则结算名次会出现"越玩越低"的错觉。
6. 鉴权、错误码、响应外壳沿用现有中间件与 `{ data }` 包装。
7. 实际库没有独立 `metric/value` 表：`sql/006_leaderboard_targets.sql` 为已验证分数与最高合成增加生成列 `leaderboard_score` / `leaderboard_number`，分别建立 `(成绩, player_id)` 索引，不修改历史迁移。
8. 接口变更后同步更新后端 `README.md`（参数、响应、错误码）。

### 4.2 `/v1/sync` 响应新增名次字段

```jsonc
{
  "data": {
    "serverTime": "2026-10-19T10:00:00.000Z",
    "cloudRevision": 12,
    "snapshot": { "...": "保持不变" },
    "rank": { "current": 13, "previous": 21 },
    "acceptedOperationIds": ["..."],
    "duplicateOperationIds": [],
    "rejectedOperations": []
  }
}
```

- `previous` = 应用本批进度操作**之前**的名次，`current` = 应用之后；两者在同一事务内计算。
- 字段放在响应顶层而非 `snapshot.progress`：名次是查询结果，不是需要持久化的快照字段。
- 幂等重放命中时 `current === previous`，客户端据此不播放箭头动画。
- 字段为**可选**：旧后端不返回时客户端必须静默降级（见第 9 节）。
- 实际实现仅在包含 `game_finished` 的同步批次返回 `rank`，普通经济校准不额外计算名次。相同请求重放仍返回原业务结果，但将 `previous` 收敛为该结果的 `current`，不重复庆祝。

### 4.3 发布顺序

1. 后端先在 `dev` 落地并通过开发环境验证（`https://leyian.online/dev/v1`）。
2. 客户端按"接口缺失即隐藏"实现，开发版/体验版/预览连 dev 接口即可联调。
3. 客户端确认无误且用户明确授权上线后，才合入 `main` 与正式客户端同步上线；设计定稿和开发环境验收不包含上线授权。
4. 客户端在接口 404、401、超时、字段缺失时都必须保持可玩、无报错弹窗。

### 4.4 新版结算快照（2026-10-20）

`/sync` 保留旧 `rank`，新增可选 `settlement: { operationId, previous, current, self, entries, celebrate }`。只对应该批次最后一条结算操作，最后一条被拒绝则不返回；客户端严格匹配操作 ID。起点使用最后一局执行前已合并的历史最佳名次，终点与条目使用同一事务中的公开榜口径。

本人单独返回，沿途最多七段共 56 条真实对手条目。大幅跃升压缩中段，不编造玩家；首次起点为 null，零分不上榜，持平与幂等重放不庆祝。无需数据库迁移或新请求参数。完整契约与验证见 [新版结算实现验证](新版结算-实现验证.md)。

## 6. Prefab 规格：固定得分区与双槽目标区

当前为无背景签、标题「得分」、暖黄色当前分数、奶油白目标分数，所有文字水平；目标不显示常驻状态前缀或分隔圆点。以下排版及动画已确认并接入代码，浏览器检查不替代 Creator 与真机验证。

### 6.1 路径与加载方式

- 路径：`assets/resources/Gameplay/ScoreTargetHUD.prefab`。静态维护的是节点结构，数字由运行时 Label 实时更新。
- 原分数是场景普通节点，现由新组合 Prefab 接管，原节点仅保留为失败回退。通过 `resources.load('Gameplay/ScoreTargetHUD')` 加载，挂在 `Status/Content` 下。
- 实例化、Label 引用检查和首次渲染成功后，关闭旧 `Score` 并停止旧分数 Tween；失败时保留旧分数。
- 已创建组合 Prefab 与脚本，现有场景 `Score` 保留为加载失败回退；未新增位图素材。

### 6.2 排版与层级

定稿根节点为 248×162、scale 1，375 宽屏幕上约 124×81 像素。上方得分区固定，下方窗口单独替换目标。两个目标槽的头像、昵称和分数必须成组提交。

```text
ScoreTargetHUD               UITransform 248×162，anchor 0.5/0.5，rotation 0
├─ CurrentScoreTitle         Label「得分」22px，240×26，pos(0, 68)，右对齐
├─ CurrentScoreValue         Label，Eazy 48px，240×56，pos(0, 27)，右对齐，暖黄 + 暖棕描边
├─ TargetViewport            248×80，pos(0, -41)，只裁切目标动画
│  ├─ TargetSlotA            240×68，pos(0, 0)
│  │  ├─ Avatar              48×48，最宽文本时 pos(-96, 0)，短文本时随实际字宽右收
│  │  ├─ Name                24px，176×26，pos(32, 21)，右对齐、单行省略
│  │  └─ Score               Eazy 36px，176×42，pos(32, -13)，右对齐
│  ├─ TargetSlotB            相同结构，稳定时只有一个槽启用
│  └─ TopContent             同位置显示「已登顶」，与头像目标互斥
```

- 得分字框及右边缘固定，常规分数保留设计字号；数字超出字框时使用 Label SHRINK 缩小实际字号，完整显示，不扩宽整组、不补前导零、不旋转，不烘焙数字图片。
- 当前数字使用暖黄 `#FFD679`，目标数字奶油白 `#FFF9ED`，配单层暖棕 `#62391F` 描边；无厚影、挤出、背景板或新增装饰。浏览器描边总宽为标题/昵称 2px、当前分数 4px、目标分数 3px；Creator 的 LabelOutline 以实际渲染校样确认，不直接混用描边参数口径。
- 得分标题、当前分数、昵称和目标分数统一靠右，文字字框右边缘均为根节点局部 x=120；头像按昵称与分数的较大实际字宽定位，保留 16 设计单位间距。昵称限定 176 宽，超宽追加 `...`；不能挤占数字字框。
- `self` / `rival` 仅改变目标数据，不恢复「即将超越」等前缀；`top` 使用原目标窗口显示「已登顶」。隐藏目标时得分区保持原位。
- 数字复用 EazyChatR.ttf；本局/目标屏幕字号约 24/18，昵称约 12。六位与七位保留设计字号；更大的分数若超宽则在固定字框中缩小，完整显示后端允许的最高分 1000000000（10 位），不使用「万」、K 或数字省略。头像的左移范围以 176 宽文本区域为限，不被超宽数字挤出窗口。
- 浏览器主分数 8000000 的字宽与描边在 248 设计单位内可容纳；Creator 的字体基线与裁切仍需检查。

### 6.5 A → B 交替动画定稿

| 阶段 | 持续 | 动作 |
| --- | ---: | --- |
| 已超越反馈 | 140ms | A 头像 1 → 1.10 → 1，细边短暂变叶绿 |
| A 退出 | 140ms | 头像、昵称、分数组成一组，向上 20 设计单位并淡出，cubicOut |
| B 接入 | 220ms | B 整组从下方 20 到原位，前 110ms 淡入完成，整段 220ms 轻微 backOut，回弹约 2 设计单位 |
| 总计 | 500ms | 上方得分区、根节点、窗口尺寸与旋转角度均不动 |

演示先用 220ms 将 579872 补间至 580128，再播放 500ms 目标交替；按钮演示总长 720ms，不能将 220ms 计分演示算入交替时长。

- 真实分数严格超过 A 且下一目标就绪后才触发；同分、首次进入、续局恢复和资料刷新不播放超越动画。动画只读状态，不反写玩法。
- 连锁一次越过多位时直接 A → 最终有效 B；动画期间只保留一个最新待切换目标，不将所有中间目标排成长队。分数补间与落子继续独立运行。
- 两槽预备完整数据与头像；异步头像必须校验槽位代次，失败使用既有默认头像。下一目标未就绪前保留 A，数据就绪后再交替，避免空白或错配。
- 没有更高目标时，在同一窗口接入「已登顶」。暂停/隐藏时收敛到最新完整目标；重开或销毁时停止两槽与分数对象的 Tween 并释放头像。
- 详细时序、连续超越与验证边界见 [目标交替动画设计](原型-超越目标与结算名次/目标交替动画设计.md)。

## 7. 本局三态逻辑

### 7.1 进局准备

```text
1. session.status !== 'authenticated'      → 目标区隐藏，得分区保留，不发请求
2. GET /profile（已存在）                   → profileBest = highestScore，自身昵称/头像
3. profileBest ≤ 0                         → 目标区隐藏，本局不发排行榜请求
4. GET /leaderboard/target?value=profileBest&limit=5
   ├─ 成功 → selfBest = max(profileBest, 响应 self.value)，缓存 entries 与 selfRankBefore
   └─ 失败/404/超时 → 目标区隐藏，不阻断对局
```

进局请求之前没有榜单 `self.value`，不能将它作为首个请求的参数。收到响应后再取历史分最大值，避免云同步延迟导致目标倒退。

### 7.2 目标解析与同分边界

```text
score = 真实本局分数（不是 Label 的补间值）
if (score ≤ selfBest)                           → { kind: 'self', 自身数据, selfBest }
else 取缓存 entries 中 value ≥ score 的最小者
    存在                                         → { kind: 'rival', ... }
    不存在且已确认无更多目标                       → { kind: 'top' }
    不存在且缓存尚未补齐                           → 保留上一条完整目标，等待数据层补齐
```

- `score === A.value` 时仍显示 A，不播放超越动画。只有 `score > A.value` 后才允许更换；一次加分恰好达到 B 的分数时显示 B，继续等待严格超越。
- HTTP 接口仍返回 `value > 查询基线`。缓存不足时，数据层使用 `value=max(已缓存最后分数, max(0, score-1))` 补查；整数分数减一用于保留恰好同分的新目标。已严格超过的同分玩家一起跳过，无须逐个展示。
- `PlayController.buildUiState()` 内的解析只读缓存，不在纯解析或 UI 渲染中发请求；补查由 `OvertakeRivalStore` 在局内进度更新流程中按第 7.3 节限流处理。
- 相同目标只更新变化字段；只有真实超越导致目标标识变化时才执行第 6.5 节交替。进局、资料刷新和续局恢复直接显示当前有效目标。

### 7.3 请求节奏

| 项 | 取值 |
| --- | --- |
| 每局请求上限 | 6 次 |
| 请求最小间隔 | 1.5s |
| 缓存有效期 | 5 分钟（重开可复用） |
| 失败退避 | 指数退避，单局最多重试 2 次 |
| 并发 | 同页请求去重，只保留一个在途请求 |

正常一局只有 1~2 次请求：进局预取一次，超越 5 人后再补一次。
