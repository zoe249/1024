# 游戏主题切换与方块皮肤开发方案

日期：2026-10-09；架构修订：2026-10-23

适用：Cocos Creator 3.8.8、微信小游戏、Web 预览。  
状态：架构设计与实施建议，未实现接口、数据库或资源发布。本文中的价格、阈值、活动周期为建议初始值，需通过开发环境试玩调整。

## 1. 核心决策

采用“本地完整 Base + 本地 Theme 按需覆盖”的两层架构，最终显示由统一解析器生成：

```text
Base：当前完整外观，提供所有必需资源和样式
  +
Theme：当前主题，只声明需要改变的资源和样式
  ↓
ResolvedAppearance：供各界面使用的完整外观
```

- **Base 层承接现有外观**，包括背景、方块、按钮、面板及配色。未选择主题时直接显示 Base；原有分散路径和 UUID 逐步收口到资源配置中。
- **Theme 层是部分覆盖配置**，只换背景的主题不用复制默认方块、按钮或弹窗；带方块皮肤的主题覆盖它明确提供的方块项，其余仍继承 Base。
- **所有素材与外观配置保存在客户端仓库，随客户端构建发布**。可以按本地 Asset Bundle 或微信分包组织，不由业务服务器或独立静态源站托管外观图片。
- **服务器如接入，只管理目录可见性、权益、碎片、奖励与所选主题 ID**。客户端根据本地目录解析 ID，不接受服务器提供的图片 URL 或任意文件路径。
- **当前只确定 Base + Theme 两层**。独立装备方块皮肤及其与主题自带皮肤的优先级尚未确定，不预先增加第三层。历史方案的奖励与碎片数值仍是候选规则，不代表已确认产品需求。
- **第一期只在首页切换，进入游戏时固定本局外观**。局中到期允许本次前台对局继续显示，到下一局或恢复入口重新校验。

首期接入背景、棋盘配色、HUD 配色及方块图层和色阶，之后逐个接入按钮和弹窗。布局仍由 Creator 场景和 Prefab 维护，主题配置不改变玩法和棋盘尺寸。

## 2. 当前项目基础与接入位置

以下结论来自本地客户端代码检查；尚未核实独立后端仓库的现有表结构和成绩验证实现。

| 文件/模块 | 当前情况 | 建议接入方式 |
| --- | --- | --- |
| `assets/script/gameplay/PieceController.ts`、`PieceStyle.ts` | 数值样式已抽到 `PieceStyle.ts`；方块图层来自 Prefab | 接收解析后的图层与样式；继续使用同一个 `piece.prefab` |
| `assets/script/gameplay/PlayUIController.ts` | 写死背景/图标 UUID、HUD/棋盘颜色，下一颗另有色表 | 统一接收解析后的主题；预览共用方块样式解析；棋盘仍仅由 `ensureBoardDecorations()` 绘制 |
| `assets/script/home/StartPageController.ts` | 固定 Homepage 资源路径，已有 SpriteFrame 时跳过加载 | 将首帧默认引用与主题应用分开；不能因已有贴图而跳过主题覆盖 |
| `assets/script/gameplay/PlayController.ts` | 管理棋子生成、技能、结算和纯数据 UI 状态 | 创建棋子时注入本局外观；业务不感知本地素材路径 |
| `assets/script/loading/LoadingSceneController.ts` | 预加载 game 场景后切场景 | 增加所选外观准备任务；超时使用本地默认外观 |
| `assets/script/gameplay/OngoingGameSession.ts` | 保存棋盘等纯数据，跨场景续局 | 可添加可选的主题 ID/本地配置版本，不保存 Bundle、节点或 SpriteFrame |
| `assets/script/online/api/GameApiClient.ts` | 已有登录、资料、排行榜和同步接口 | 增加外观目录、背包、领取、兑换、装备方法 |
| `assets/script/online/sync/PlayerSyncOutbox.ts` | `game_finished` 上报客户端生成的 gameId、score、highestNumber；队列上限 200 | 可用作成绩传输入口；不能直接当奖励授权凭证，不能依赖会被裁剪的队列保存重要领取请求 |
| `assets/script/economy/PlayerEconomyStore.ts` | 现有金币、体力、技能经济仓库 | 碎片首期单独由外观仓库读取服务端余额，避免改变既有离线经济同步 |
| `assets/script/online/api/OnlineServiceConfig.ts` | 已按 API 地址隔离存储，并自动选择开发/正式接口 | 外观权益和请求记录进一步按玩家 ID 隔离 |

必须保持：`assets/scence/` 路径、原场景层级、已有 UUID 和序列化属性；棋盘位置和尺寸仍由 `BoardGeometry` / `BoardConfig` 决定。兼容 `SkliisController`、`SkillsController` 两种节点名。

## 3. 获取规则与生命周期（候选产品规则）

本节沿用历史方案的数值建议，不作为本次架构确认的实施前提。其中“方块主题”指只覆盖方块的 Theme 配置，与背景主题共用当前主题选择入口；独立皮肤商品和自由搭配待后续确认。

### 3.1 分数达标领取 7 天

建议第一期配置两项示范奖励：

| 活动规则 ID（示例） | 条件 | 奖励 | 限领 |
| --- | --- | --- | --- |
| `score_theme_forest_launch` | 活动期内一局已审核通过成绩 ≥ 10,000 | 森林主题 7 天 | 每个账号本活动一次 |
| `score_theme_jelly_launch` | 活动期内一局已审核通过成绩 ≥ 20,000 | 果冻方块主题 7 天 | 每个账号本活动一次 |

1. 使用单局最终成绩，续局仍属于同一局；暂停、退出首页不产生第二次结算。
2. 服务器按已接受的成绩记录判断资格，客户端仅展示进度。达到阈值显示“可领取 7 天”，用户点击领取时开始计时。
3. `expiresAt = serverNow + 604800 秒`，精确到时间戳；不是第七个自然日零点。
4. 领取必须在活动领取截止时间前完成；已领取权益不因活动结束提前消失。活动时间统一由服务器保存 UTC，界面显示本地时间。
5. 活动条件用 `ruleVersion` 固化。修改同一活动数值不重置领取次数；新的奖励机会必须创建新的活动 ID。
6. 不补发历史本地最高分；上线前的历史成绩如需补偿，独立建立可审计迁移规则。

未来若需要“消费积分买 7 天”，另建 `style_points` 钱包与积分流水。不要扣减单局成绩、最高分或排行榜记录。

### 3.2 碎片兑换永久

第一期只引入一种通用“装扮碎片”，余额为非负整数，减少玩家理解成本和库存类型。

- 示例价格：永久森林主题 100 碎片，永久果冻方块主题 60 碎片。
- 示例来源：每天第一局审核通过且分数 ≥ 2,000，发 2 碎片；当天审核通过最高分首次达到 10,000，再发 3 碎片。两项可叠加，每天最多 5 碎片，按服务器 `Asia/Shanghai` 日期归档。
- 不考虑额外活动时，主题最快 20 天、皮肤最快 12 天。该速度仅为初始调参基线。
- 领奖与碎片条件均由服务端判定；客户端不上传“应增加多少碎片”。如以后接签到或广告，必须接服务端认可的奖励来源。
- 永久兑换在线执行；扣碎片、写权益、写流水在同一个数据库事务内完成。
- 已永久拥有时再次兑换不扣款，返回 `ALREADY_OWNED`。在 7 天试用期间兑换，立即升级永久，不额外返还剩余时长或碎片。

### 3.3 重复获取、续期与过期

| 当前状态 | 获取相同物品时的行为 |
| --- | --- |
| 未拥有/已过期 | 新限时奖励从服务器当前时间起算 |
| 限时有效 | 另一个合法奖励来源可叠加：`max(expiresAt, now) + duration`；同一来源重试绝不延长 |
| 已永久拥有 | 限时活动显示“已永久拥有”，不继续领取，不自动折算碎片 |
| 限时有效并兑换永久 | `permanent=true`、`expiresAt=null`，永久状态优先 |
| 已装备且到期 | 界面显示已过期；下一局或恢复入口回退完整 Base |

是否可使用由 `permanent || expiresAt > serverNow` 判断，不靠定时任务把数据库改成“过期”。有效期不能用 `null` 同时表达未拥有和永久，必须有明确的 `permanent` 字段。

服务端保留用户选择的 `selectedThemeId`；客户端派生实际 `effectiveThemeId`。到期时实际显示回退 Base；再次获得同一物品后，若用户未改选其他主题，则在下一次进入场景时恢复原偏好，并在领取结果中提示。资源准备失败只回退本次显示，不撤销权益、不扣第二次碎片。Base 始终可用，不需要额外授予其使用权。

## 4. 玩家操作与界面状态

候选界面：首页增加“装扮”入口，按背景或方块覆盖范围分类展示，上方显示碎片余额。分类不代表多个装备槽；首期静态布局在 Creator 维护。

卡片显示缩略图、名称、获取方式、权益和装备状态。权益状态与资源状态分开表示：

- 权益：未拥有、可领取、限时有效、永久、已过期。
- 资源：未准备、准备中、就绪、准备失败、当前客户端不支持。
- 装备：已选择、实际使用、默认回退。

未拥有也可在独立预览区看效果，但预览绝不写装备。永久兑换弹窗显示确切价格和剩余余额；请求中禁用重复点击。领取成功即展示权益，资源准备失败提示“已获得，外观准备失败，可重试”。

点击“使用”的流程：校验已登录和权益 → 加载必要资源 → 向服务器保存装备 → 应用首页预览。加载失败保留原装备；装备请求结果不明时先刷新状态，不立即认为失败并覆盖服务端结果。服务器在装备请求提交时再次检查到期时间。

预览区与正式界面使用同一个 Base + Theme 解析器，完整展示继承后的结果；数字必须始终清晰。错误与倒计时文案不得只用颜色表达。后续若增加独立装备皮肤，再单独确定它与主题自带方块外观的关系。

## 5. 客户端模块架构

### 5.1 两层覆盖规则

最终外观始终由 `resolveAppearance(base, theme.overrides)` 生成。覆盖按固定字段和资源用途处理，不用整组替换或不受约束的通用深合并：

| 情况 | 最终显示 |
| --- | --- |
| 没有选择主题 | 完整 Base |
| 主题只配置游戏背景 | 主题背景；方块、按钮、面板和配色继承 Base |
| 主题配置背景和方块皮肤 | 使用主题明确提供的背景、方块项；其他项继承 Base |
| 主题只配置某个方块图层或某个数值样式 | 只覆盖对应项，未提供的图层、数值和字段继承 Base |
| 从主题 A 切到主题 B | 重新计算 Base + B；B 未覆盖的项恢复 Base，不保留 A 的残留 |
| 取消主题、主题失效或当前客户端没有该主题 | 回到完整 Base |

字段省略或为 `undefined` 表示继承 Base。透明度 `0`、布尔值 `false` 等明确值不能被当成缺省；需要隐藏可选装饰时使用明确的 `enabled: false`，不拿空路径或 `null` 同时表达继承与隐藏。必需资源不允许清空。

方块按图层、数值和样式字段合并；合并后校验贴图与染色模式等关联约束。完整彩色贴图使用白色 Sprite 色值，避免继承 Base 染色后再次乘色。仅省略配置属于正常继承；已声明覆盖但资源缺失属于配置或加载错误，不能悄悄当作“未覆盖”。

解析器生成完整的纯数据描述，资源加载器再解析为 SpriteFrame 等表现资源。界面使用解析结果，不各自重复判断“主题有没有这张图”。进入一局后固定解析结果，不能因加载先后顺序改变当前显示。

### 5.2 模块与数据流

建议新增目录 `assets/script/appearance/`，先落地 Base、主题描述、解析器和必要的资源入口；权益与商城模块后续按需求接入。

| 模块 | 职责 |
| --- | --- |
| `AppearanceTypes.ts` | 完整 Base、可选 Theme 覆盖、解析结果与本地资源标识的类型 |
| `BaseAppearance.ts` | 当前完整默认外观的配置；集中维护默认资源入口和样式 |
| `AppearanceCatalog.ts` | 随客户端发布的本地主题 ID、配置版本、Bundle 名称与覆盖清单 |
| `AppearanceResolver.ts` | 按白名单字段合成 Base + Theme，校验关联约束，不访问节点或网络 |
| `PlayerAppearanceStore.ts` | 玩家权益、碎片、服务端时间基线、revision、装备偏好；不持有节点 |
| `AppearanceService.ts` | 编排领取、兑换、装备和刷新；UI 只能通过它发送操作 |
| `AppearanceAssetLoader.ts` | 解析现有默认引用与本地 Bundle 资源，负责加载去重、失败处理和资源引用 |
| `AppearanceRuntime.ts` | 本次场景/对局的已解析外观；管理资源租约，不写玩家权益 |
| `AppearancePopupController.ts` | 渲染纯数据状态，通过回调发出操作 |

数据流：

```text
Base 配置 + 本地 Theme 覆盖 → Resolver → 完整外观描述
                                         ↓
                           AssetLoader → Runtime（资源租约）
                                         ↓
             首页主题视图 / PlayUIController / PieceController

可选服务端权益 → Store → Service → 从本地目录选择合法主题 ID
UI 点击 → 回调 → Service → 新快照 → UI 更新
```

主题使用固定用途标识和样式字段，例如 `game.background`、`piece.layers.body`、面板底色、标题文字、棋盘底色、分隔线和落点提示色。具体资源路径或现有引用集中在本地配置及绑定入口；场景和业务脚本不再散落主题判断。主题不控制棋盘尺寸、节点路径、碰撞或玩法参数。

皮肤描述使用 `stylesByValue` 和 `fallbackStyle`，覆盖 2～8192，超过范围有确定回退。继续由 Label 渲染数字。支持“白底图层染色”和“完整彩色贴图”两种模式；完整彩色贴图的 Sprite 色值必须为白色，避免重复乘色。

`PieceController` 增加 `applyAppearance(resolvedStyle)`，让 `setValue()` 和布局刷新均读取注入样式。默认样式严格复刻当前视觉。当前 `getSpriteFrame()` / `getBackgroundColor()` 用于技能与合并临时表现，必须与新皮肤一致；下一颗预览也使用同一解析器，不能只替换棋盘内棋子。

`PlayUIState` 如需增加外观信息，只放必要的主题 ID/版本，不放资源对象或文件路径。资源仍由初始化/独立表现入口注入，保留玩法与渲染边界。未接入的界面先显示 Base，接入时必须显式刷新当前引用，不能因节点已有 SpriteFrame 而跳过覆盖。

## 6. 素材放在哪里

### 6.1 存储分工

| 内容 | 建议位置 | 原因 |
| --- | --- | --- |
| Base 素材 | 客户端现有 `assets/images`、`assets/resources`、Prefab 与场景引用 | 保留现有 UUID，逐步集中配置，不要求先整体搬文件 |
| Theme 覆盖配置、导入图片 | 客户端仓库 `assets/appearance-bundles/`；设计母版放既有设计目录 | 每个主题只提交它需要覆盖的配置与素材 |
| 已构建的主题资源 | 客户端发布包，按本地 Bundle 或微信分包组织 | 无需自行部署静态资源服务 |
| 缩略图 | 客户端本地目录，随版本发布 | 列表预览不必先加载完整主题 |
| 玩家权益与活动 | 可选业务 API；按环境与玩家隔离缓存 | 与素材存储分开 |

Base 和 Theme 属于逻辑层，不要求物理目录各存一套完整图片。主题继承的 Base 素材直接复用，避免为每套主题复制方块、按钮和弹窗。服务器不保存图片、Bundle 文件或素材路径。

### 6.2 目录约定

以下为建议新增目录，不要求迁移现有 Base 素材：

```text
assets/appearance-bundles/
  theme_forest_v1/          # 本地主题，只覆盖背景
    manifest.json          # 只声明 game.background 等覆盖项
    textures/background.png
  theme_jelly_v1/           # 本地主题，覆盖方块外观
    manifest.json          # 只声明需要覆盖的方块项
    textures/body.png
    textures/shadow.png
    textures/outline.png
    textures/highlight.png
    textures/crown.png
```

本地目录集中记录 `themeId`、配置版本、Bundle 名称和包内资源路径。目录必须与构建产物一起发布；服务端返回的主题 ID 只有在本地目录存在并兼容时才可使用。新增图片或表现能力需要发布客户端版本，不能仅靠修改服务端目录增加客户端不存在的素材。

Cocos Asset Bundle 支持本地存放，也可配置为小游戏分包。具体配置由 Creator 完成，构建后检查资源及依赖是否进入预期包；不能只用源码目录名判断最终分包。主题之间不交叉依赖，Base 与主题共享资源的实际归属和加载顺序需检查构建结果。[官方 Bundle 文档](https://docs.cocos.com/creator/3.8/manual/zh/asset/bundle.html)

保留场景、Prefab 和资源 UUID；后续若确需移动或配置资源，作为独立资源重映射任务验证，本次文档修订不修改 `.meta`。避免将全部候选主题静态引用进启动场景而失去按需加载的意义。

### 6.3 文件与内存预算

建议首期预算（不是引擎或平台承诺）：单主题新增资源 ≤ 1.5 MB、其中方块覆盖资源 ≤ 500 KB、单缩略图 ≤ 40 KB；超标需评估实际体验。Base 复用素材不计为每个主题各复制一份，但最终包体仍按真实依赖核算。主包遵守仓库 4 MB 上限，必须以真实构建产物核算，不用源码目录大小代替。

PNG 压缩体积不等于显存：1024×2048 的 RGBA8 纹理仅基础像素约 8 MiB，尚未计 mipmap 和其他开销。只保留默认外观、当前外观及一个预览候选，列表缩略图按可见区域加载。

方块首期沿用现有 160×160 透明画布约定，检查 Alpha 有效尺寸，保留 `trim=false` 和相对棋子尺寸布局；背景按常规屏幕、长屏安全区检查裁切。棋盘装饰不能烘焙出固定 5×7 格子，需继续适配合法尺寸。

真正制作/替换 UI 位图时必须先完整阅读 `Skills/cocos-cream-ui-assets/SKILL.md`，执行其像素、Alpha、运行时大小、体积及预览检查。本次只写方案，没有生成或替换素材。

## 7. 如何解析、加载与切换

### 7.1 加载流程

1. 启动先准备并显示完整 Base。读取本地主题目录；接入权益后再刷新玩家可使用的主题。
2. 根据选中的主题 ID 找到本地覆盖配置，验证字段、配置版本和平台兼容性。未知 ID 回退 Base，不拼接服务器传入的路径。
3. Resolver 先合成完整描述；AssetLoader 复用已准备的 Base 资源，只额外准备当前主题需要的覆盖资源。同一 `(平台, bundleName, 本地配置版本)` 合并重复请求。
4. 用户切换时，完整准备候选外观后再一次性绑定。确认任务仍为最新、宿主仍有效、账号未切换，再保存并应用选择。
5. 主题省略某项时继承 Base；已声明覆盖项加载失败则报错。首页主动切换失败保留原选择，进入场景准备失败则整套回退 Base，不能显示半套候选主题。
6. 进入 loading 后，并行预加载 game 场景和本局外观。建议外观最多等待 5 秒，失败使用 Base；场景预加载失败单独报错。退出时释放候选租约并作废在途任务。
7. game 创建前固定本局外观；所有棋子、下一枚、结算缩略图和临时特效读取同一解析结果。晚到的加载结果不在落子中途替换外观。

资源入口按清单中的本地 Bundle 名称加载，再按包内路径获取资源。既有 Base 序列化引用由适配入口收集；不要求为接入主题先把全部默认素材迁进新目录。SpriteFrame 子资源路径和构建依赖必须在 Creator 中核对。[官方 Bundle 文档](https://docs.cocos.com/creator/3.8/manual/zh/asset/bundle.html)

### 7.2 版本与资源生命周期

- 素材在本地不等于已拥有对应权益。若接入限时或付费权益，资源加载与账号授权仍分别校验。
- `AppearanceAssetLoader` 对外提供 `acquire()` / `release()` 租约。同一资源被首页预览、棋子或临时特效使用时不能提前释放。
- 替换顺序：完整准备新外观 → 一次性绑定 → 清理旧预览/临时节点 → 释放旧租约。超时回调也要回收其新建资源。
- 共享图层不能被单颗棋子的 `onDestroy()` 直接销毁。退出场景解绑监听，停止 Tween、定时器，销毁动态预览节点。
- Bundle `removeBundle()` 不等价于释放其已加载资源；`releaseAll()` 可能影响外部依赖，仅在确认租约归零、引用已解除后使用。[官方资源释放说明](https://docs.cocos.com/creator/3.8/manual/zh/asset/bundle.html)
- Base 资源与主题继承项可能共用同一资产，不能因卸载主题而释放仍被 Base 使用的资源。主题 A 切到 B 时重新从 Base 解析，不在 A 的结果上增量打补丁。
- 本地资源随客户端版本更新；旧快照中的未知主题 ID 回退 Base。若使用微信分包，需覆盖该分包尚未可用或准备失败的情况，不能把“本地发布”理解为所有资源始终已加载到内存。

## 8. 服务端模型与一致性

下列是逻辑模型，实施前检查后端现有表，复用已有玩家、幂等和经济流水能力。不要假定这些表已存在。

| 逻辑表 | 关键字段/约束 |
| --- | --- |
| `cosmetic_items` | `item_id` 主键；本地主题 ID、名称、状态、最低客户端版本；状态区分在售、停售、禁用 |
| `cosmetic_releases` | 可选的客户端兼容记录；物品 ID、平台、本地配置版本、最低客户端版本；不保存图片 URL 或包内路径 |
| `cosmetic_offers` | offer ID、ruleVersion、活动时间、领取截止时间、阈值/碎片价格、奖励时长、次数限制 |
| `player_cosmetic_entitlements` | `(player_id,item_id)` 唯一；`permanent`、`expires_at`、更新时间 |
| `player_cosmetic_wallets` | player 主键；fragment balance 非负整数、revision |
| `player_cosmetic_equipment` | player 主键；selected theme ID、独立递增 appearance revision |
| `cosmetic_grant_ledger` | 来源类型、source ID、player、item、增量、兑换前后状态；业务来源唯一索引 |
| `cosmetic_fragment_ledger` | player、来源 ID、正负 delta、余额、发生时间；来源唯一索引 |
| `cosmetic_requests` | `(player_id,operation_id)` 唯一；请求摘要、状态与响应结果；相同键不同参数拒绝 |
| `verified_game_results` | 可复用成绩表；player、稳定 game ID、审核状态、score、结束时间、活动归属 |

所有外观权益/钱包/装备变更在事务中递增该玩家的 `appearanceRevision`；客户端只接受不旧于当前 revision 的快照，与既有 `cloudRevision` 分开。目录用独立 `catalogVersion`。

### 8.1 永久兑换事务

1. 从登录凭证确定 playerId，不接受客户端指定受益玩家。
2. 按统一顺序锁定该玩家的外观状态行和钱包行，检查 operationId；已完成则重放原结果。
3. 读取并验证 offer、当前规则版本、物品状态、既有永久权益；客户端只提交 offer ID，不提交可信价格。
4. 若客户端所见 `ruleVersion` 已变化，返回 `OFFER_CHANGED`，显示新价格后由用户重新确认，不自动提高扣费。
5. 条件扣余额（余额必须 ≥ 价格），写永久权益、负数碎片流水、权益流水、新 revision 和幂等结果，同事务提交。
6. 超时或断网后用原 operationId 重试；不得换 ID 猜测交易结果。并发不同 ID 兑换同一物品也必须在锁内检查永久权益，保证不重复扣款。

领取限时奖励采用相同事务原则，并额外对 `(player,offer,活动领取周期)` 建唯一约束。客户端 operationId 只能防网络重试，业务唯一键才能防换 ID 重复领。

### 8.2 成绩可信度与对局标识

当前客户端 `recordGameFinished()` 在记录完成时生成 gameId，并上报分数；从客户端代码无法证明服务器具备防作弊能力。给数字加签、加密本地存档或限制阈值都不能证明成绩真实。

建议奖励对局新增服务器签发的 `runId`，开局时绑定玩家、游戏规则版本和开始时间，写入 `OngoingGameSession` 纯数据快照。续局沿用 runId，完成结算只有一份记录；不能在重试或返回首页时生成新 runId。

首期最低校验：合法规则版本、合理时长、分数/最大方块边界、提交频率、对局状态和重复结束；异常记录待审核，不发奖励。该层只能降低滥用，不能完全证明成绩。价值较高的活动需增加确定性随机种子、输入操作序列和服务端重放，明确额外开发成本。

建议首期奖励只接受在线开局并在活动期间完成、及时提交审核的对局；纯离线或旧客户端无 runId 的成绩仍可保留普通进度，但不直接获得装扮奖励。若允许离线奖励，必须另行定义可信时间与重放方案，不能凭客户端 `occurredAt` 跨天补领。

`game_finished` 同步被确认仅表示数据已接收，奖励资格必须等待 `verificationStatus=accepted`。优先在现有成绩处理后复用审核结果发碎片，避免再开一条独立成绩上报通道。旧 outbox 的 200 条裁剪不能承担重要未确认交易；领取、兑换和装备的待确认 operationId 存单独小型持久记录，完成后删除。

## 9. 建议接口契约

以下均为新增设计，沿用 `GameApiClient` 的 `{ data: ... }` / `{ error: ... }` 包装。开发请求基址为 `https://leyian.online/dev/v1`，正式为 `https://leyian.online/v1`。

| 方法与路径 | 请求 | 返回要点 |
| --- | --- | --- |
| `GET /cosmetics/catalog?platform=wechat&clientVersion=...` | 平台、客户端版本 | catalogVersion、serverTime、items、offers、releases |
| `GET /me/cosmetics` | 登录凭证 | serverTime、appearanceRevision、碎片、权益、装备、活动进度/可领状态 |
| `POST /me/cosmetics/claims` | operationId、offerId、ruleVersion | 完整玩家外观快照、grantId |
| `POST /me/cosmetics/exchanges` | operationId、offerId、ruleVersion | 完整快照、兑换结果 |
| `PATCH /me/cosmetics/equipment` | operationId、expectedRevision、themeId | 完整快照；并发冲突返回最新 revision |

`platform=web` 使用对应 Web 产物。服务端目录只提供物品、活动和兼容信息；本地目录决定资源与覆盖内容。每次修改返回完整的小型外观快照，避免客户端分别加余额、加权益造成部分更新。装备接口当前只支持主题槽。

示例玩家快照：

```json
{
  "data": {
    "serverTime": "2026-10-09T08:00:00Z",
    "appearanceRevision": 12,
    "fragments": 35,
    "selectedThemeId": "theme_forest",
    "entitlements": [
      { "itemId": "theme_forest", "permanent": false, "expiresAt": "2026-10-16T08:00:00Z" }
    ],
    "claimableOfferIds": []
  }
}
```

物品兼容记录示意字段：`itemId=theme_forest`、`platform=wechat`、`appearanceConfigVersion=1`、`minClientVersion=内置此主题的客户端版本`。Bundle 名称、资源路径和覆盖字段仅存在客户端本地目录；服务器不能通过下发资源地址改变其内容。版本比较应解析版本段，不用字符串字典序。

建议业务错误：`SCORE_NOT_QUALIFIED`、`ALREADY_CLAIMED`、`ALREADY_OWNED`、`INSUFFICIENT_FRAGMENTS`、`OFFER_CHANGED`、`OFFER_CLOSED`、`ENTITLEMENT_EXPIRED`、`ITEM_DISABLED`、`REVISION_CONFLICT`。沿用既有未登录/超时错误处理。

## 10. 时间、离线、账号与续局

- 同一前台运行内以服务器时间为基线，加单调时钟 elapsed 估算倒计时，不能用设备当前日期直接续命。
- 回到前台、进入新局、恢复存档和装备前刷新权益；限时权益校验请求失败则保守回退默认项。倒计时变负只改变展示，不在客户端删除服务器记录。
- 冷启动离线时，已缓存的永久权益与当前可准备的本地资源可继续用于该账号的外观展示；限时权益需联网确认。永久缓存只是客户端便利，不是服务器可接受的授权证明。
- 已在前台进行的一局到期或临时断网，保留本局显示；跨场景续局或从后台恢复是新的校验入口。明确不以“一直保存续局”无限延长租期。
- 游客可使用默认外观和预览，领取/兑换需登录。游客本地余额、最高分不直接导入永久权益。
- 存储键采用 `getOnlineStorageKey('appearance-v1') + ':' + playerId`；退出登录立即清理内存权益、装备候选与未完成回调。资源文件可按环境共享缓存，权益绝不跨账号共享。
- 用户恢复旧存档时新增字段均可选；缺失则取当前合法主题/Base。当前客户端不含快照指定的主题或配置不兼容时回退 Base，不阻止恢复棋盘。
- 多设备冲突按服务端 revision 解决；装备失败后刷新并提示重试，不用客户端时间判定“最后操作”。

## 12. 实施拆分与验收

### 阶段一：本地外观解耦

交付完整 Base、可选 Theme 类型、逐字段解析器、皮肤注入和统一资源入口。先将当前外观接入 Base，证明未覆盖项完全保持原显示。

主要文件：新增 `appearance/AppearanceTypes.ts`、`BaseAppearance.ts`、`AppearanceCatalog.ts`、`AppearanceResolver.ts`、`AppearanceRuntime.ts`；修改 `PieceController.ts`、`PlayUIController.ts`、`PlayController.ts` 及首页接入点。保留现有 Prefab 属性及资源引用。

验收：默认画面无回归；只换背景时方块、按钮和弹窗继承 Base；覆盖部分方块项时其他项仍继承；数字/下一颗/技能碎片一致；5×7 及其他合法尺寸正确；普通落子与合并不触发额外资源加载。

### 阶段二：本地覆盖与切换闭环

交付 AssetLoader、“只换背景”和“背景带方块皮肤”两类本地候选主题、缩略图与本地清单；接入 LoadingSceneController 和首页预览。

验收：Base → A → B → Base 无残留；字段缺省、透明度为 0、显式隐藏可选装饰、声明资源缺失、本地配置不兼容、分包准备失败、资源释放和快速退出均正确处理。主包体积按构建实测。

### 阶段三：服务端权益闭环（按产品规则接入）

交付目录、背包、领取、碎片兑换、装备 API 和事务；补齐稳定 runId、成绩审核状态和来源唯一约束。后端具体迁移文件名待核查独立仓库后确定。

客户端新增 Store、Service、API 方法；接首页入口。用本地主题验证 7 天、永久和失败重试；权益与奖励不阻塞前两阶段的架构验证。

验收：重复领取不续期，并发兑换只扣一次；已永久拥有不扣；修改本地时间不延长；开发/正式及两账号数据隔离。

### 阶段四：真机与活动调参

交付最终主题卡片、兑换弹窗、倒计时、错误提示和运营配置；开发环境完成下表后再准备上线评审。

| 验收场景 | 预期 |
| --- | --- |
| 分数差 1 分、恰好达标、超过阈值 | 仅通过审核且达标的局提供领取资格 |
| 同一个成绩/领取请求重复发送 | 只有一份奖励/碎片流水 |

| 到期瞬间、前后台切换、改设备时间 | 当前前台局不闪变，恢复/新局重新校验 |
