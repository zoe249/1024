# 游戏主题切换与方块皮肤开发方案

日期：2026-10-09  
适用：Cocos Creator 3.8.8、微信小游戏、Web 预览。  
状态：架构设计与实施建议，未实现接口、数据库或资源发布。本文中的价格、阈值、活动周期为建议初始值，需通过开发环境试玩调整。

## 1. 核心决策

采用“本地默认外观 + 远程扩展资源 + 服务端权益”的组合：

- **本地始终保留默认主题与默认方块**，无网络、资源损坏或权益过期时仍可正常玩。
- **主题和方块皮肤是两种独立物品**，分别获取、分别装备，允许自由搭配。套装只是展示组合，不隐含两种权益同时解锁。
- **分数达标领取 7 天使用权，收集碎片兑换永久所有权**。首期采用“达标奖励”，不扣游戏分数，不把排行榜分数改为货币。
- **服务器保存权益、碎片、奖励记录和装备偏好**；图片文件放静态资源存储，数据库只保存资源标识与发布信息。
- **扩展外观用无脚本的远程 Asset Bundle**，按需下载。默认外观继续沿用现有引用，不为接入系统大规模移动资源。
- **第一期只在首页装备，进入游戏时确定外观**。局中到期允许本次前台对局继续显示，到下一局或恢复入口重新校验，避免合并过程中突然换图。

第一期范围：主题背景、棋盘配色、HUD 配色，以及方块各图层和数值色阶。字体、音乐、技能图标、复杂动画和全套弹窗皮肤暂不开放给远程配置。

## 2. 当前项目基础与接入位置

以下结论来自本地客户端代码检查；尚未核实独立后端仓库的现有表结构和成绩验证实现。

| 文件/模块 | 当前情况 | 建议接入方式 |
| --- | --- | --- |
| `assets/script/gameplay/PieceController.ts` | `PIECE_STYLE` 定义数值配色；Shadow、Body、Outline、Highlight、Decoration、Value 分层显示 | 抽出默认皮肤描述；增加样式注入，继续使用同一个 `piece.prefab` |
| `assets/script/gameplay/PlayUIController.ts` | 管理 HUD、下一颗显示和棋盘装饰；存在固定颜色 | 注入主题 token；棋盘仍仅由 `ensureBoardDecorations()` 绘制 |
| `assets/script/gameplay/PlayController.ts` | 管理棋子生成、技能、结算和纯数据 UI 状态 | 创建棋子时应用本局皮肤；UI 状态传外观 ID，业务不感知素材 URL |
| `assets/script/loading/LoadingSceneController.ts` | 预加载 game 场景后切场景 | 增加所选外观准备任务；超时使用本地默认外观 |
| `assets/script/gameplay/OngoingGameSession.ts` | 保存棋盘等纯数据，跨场景续局 | 可添加可选的外观 ID/版本快照，不保存 Bundle、节点或 SpriteFrame |
| `assets/script/online/api/GameApiClient.ts` | 已有登录、资料、排行榜和同步接口 | 增加外观目录、背包、领取、兑换、装备方法 |
| `assets/script/online/sync/PlayerSyncOutbox.ts` | `game_finished` 上报客户端生成的 gameId、score、highestNumber；队列上限 200 | 可用作成绩传输入口；不能直接当奖励授权凭证，不能依赖会被裁剪的队列保存重要领取请求 |
| `assets/script/economy/PlayerEconomyStore.ts` | 现有金币、体力、技能经济仓库 | 碎片首期单独由外观仓库读取服务端余额，避免改变既有离线经济同步 |
| `assets/script/online/api/OnlineServiceConfig.ts` | 已按 API 地址隔离存储，并自动选择开发/正式接口 | 外观权益和请求记录进一步按玩家 ID 隔离 |

必须保持：`assets/scence/` 路径、原场景层级、已有 UUID 和序列化属性；棋盘位置和尺寸仍由 `BoardGeometry` / `BoardConfig` 决定。兼容 `SkliisController`、`SkillsController` 两种节点名。

## 3. 获取规则与生命周期

### 3.1 分数达标领取 7 天

建议第一期配置两项示范奖励：

| 活动规则 ID（示例） | 条件 | 奖励 | 限领 |
| --- | --- | --- | --- |
| `score_theme_forest_launch` | 活动期内一局已审核通过成绩 ≥ 10,000 | 森林主题 7 天 | 每个账号本活动一次 |
| `score_skin_jelly_launch` | 活动期内一局已审核通过成绩 ≥ 20,000 | 果冻方块 7 天 | 每个账号本活动一次 |

1. 使用单局最终成绩，续局仍属于同一局；暂停、退出首页不产生第二次结算。
2. 服务器按已接受的成绩记录判断资格，客户端仅展示进度。达到阈值显示“可领取 7 天”，用户点击领取时开始计时。
3. `expiresAt = serverNow + 604800 秒`，精确到时间戳；不是第七个自然日零点。
4. 领取必须在活动领取截止时间前完成；已领取权益不因活动结束提前消失。活动时间统一由服务器保存 UTC，界面显示本地时间。
5. 活动条件用 `ruleVersion` 固化。修改同一活动数值不重置领取次数；新的奖励机会必须创建新的活动 ID。
6. 不补发历史本地最高分；上线前的历史成绩如需补偿，独立建立可审计迁移规则。

未来若需要“消费积分买 7 天”，另建 `style_points` 钱包与积分流水。不要扣减单局成绩、最高分或排行榜记录。

### 3.2 碎片兑换永久

第一期只引入一种通用“装扮碎片”，余额为非负整数，减少玩家理解成本和库存类型。

- 示例价格：永久主题 100 碎片，永久方块皮肤 60 碎片。
- 示例来源：每天第一局审核通过且分数 ≥ 2,000，发 2 碎片；当天审核通过最高分首次达到 10,000，再发 3 碎片。两项可叠加，每天最多 5 碎片，按服务器 `Asia/Shanghai` 日期归档。
- 不考虑额外活动时，主题最快 20 天、皮肤最快 12 天。该速度仅为初始调参基线。
- 领奖与碎片条件均由服务端判定；客户端不上传“应增加多少碎片”。如以后接签到或广告，必须接服务端认可的奖励来源。
- 永久兑换在线执行；扣碎片、写权益、写流水在同一个数据库事务内完成。
- 已永久拥有时再次兑换不扣款，返回 `ALREADY_OWNED`。在 7 天试用期间兑换，立即升级永久，不额外返还剩余时长或碎片。

### 3.3 重复获取、续期与过期

| 当前状态 | 获取相同物品时的行为 |
| --- | --- |
| 未拥有/已过期 | 新限时奖励从服务器当前时间起算 |
| 限时有效 | 另一个合法奖励来源可叠加：`max(expiresAt, now) + duration`；同一来源重试绝不延长 |
| 已永久拥有 | 限时活动显示“已永久拥有”，不继续领取，不自动折算碎片 |
| 限时有效并兑换永久 | `permanent=true`、`expiresAt=null`，永久状态优先 |
| 已装备且到期 | 界面显示已过期；下一局或恢复入口回退对应默认项，另一装备槽不受影响 |

是否可使用由 `permanent || expiresAt > serverNow` 判断，不靠定时任务把数据库改成“过期”。有效期不能用 `null` 同时表达未拥有和永久，必须有明确的 `permanent` 字段。

服务端保留用户选择的 `selectedThemeId` / `selectedSkinId`；客户端派生实际 `effectiveThemeId` / `effectiveSkinId`。到期时实际显示回退默认项；再次获得同一物品后，若用户未改选其他物品，则在下一次进入场景时恢复原偏好，并在领取结果中提示。下载失败只回退本次显示，不撤销权益、不扣第二次碎片。

## 4. 玩家操作与界面状态

首页增加“装扮”入口，弹窗分“主题”“方块”两个页签，上方显示碎片余额。首期静态布局在 Creator 维护。

卡片显示缩略图、名称、获取方式、权益和装备状态。权益状态与资源状态分开表示：

- 权益：未拥有、可领取、限时有效、永久、已过期。
- 资源：未下载、下载中、就绪、下载失败。
- 装备：已选择、实际使用、默认回退。

未拥有也可在独立预览区看效果，但预览绝不写装备。永久兑换弹窗显示确切价格和剩余余额；请求中禁用重复点击。领取成功即展示权益，下载失败提示“已获得，资源下载失败，可重试”。

点击“使用”的流程：校验已登录和权益 → 加载必要资源 → 向服务器保存装备 → 应用首页预览。加载失败保留原装备；装备请求结果不明时先刷新状态，不立即认为失败并覆盖服务端结果。服务器在装备请求提交时再次检查到期时间。

主题和方块可以单独预览并组合；数字必须始终清晰。错误与倒计时文案不得只用颜色表达。

## 5. 客户端模块架构

建议新增目录 `assets/script/appearance/`，按需要逐步落地，避免一开始搭建通用商城框架。

| 模块 | 职责 |
| --- | --- |
| `AppearanceTypes.ts` | 目录、权益、装备、主题 token、皮肤描述的纯数据类型 |
| `DefaultAppearance.ts` | 当前默认样式，离线和兼容兜底 |
| `AppearanceCatalogStore.ts` | 拉取与缓存目录；校验 schema、客户端版本、平台和资源版本 |
| `PlayerAppearanceStore.ts` | 玩家权益、碎片、服务端时间基线、revision、装备偏好；不持有节点 |
| `AppearanceService.ts` | 编排领取、兑换、装备和刷新；UI 只能通过它发送操作 |
| `AppearanceAssetLoader.ts` | Bundle 加载去重、超时、失败处理、资源引用计数和版本切换 |
| `AppearanceRuntime.ts` | 本次场景/对局的已解析外观；管理资源租约，不写玩家权益 |
| `AppearancePopupController.ts` | 渲染纯数据状态，通过回调发出操作 |

数据流：

```text
服务端目录/玩家背包 → Store（纯数据） → Service（校验、编排）
                                             ↓
                               AssetLoader → Runtime（资源租约）
                                             ↓
                 首页主题视图 / PlayUIController / PieceController
UI 点击 → 回调 → Service → API → 新快照 → UI 更新
```

主题使用固定 token：背景、面板底色、标题文字、正文文字、棋盘底色、分隔线、落点提示色。远程数据只允许白名单字段，不控制棋盘尺寸、节点路径、碰撞或玩法参数。

皮肤描述使用 `stylesByValue` 和 `fallbackStyle`，覆盖 2～8192，超过范围有确定回退。继续由 Label 渲染数字。支持“白底图层染色”和“完整彩色贴图”两种模式；完整彩色贴图的 Sprite 色值必须为白色，避免重复乘色。

`PieceController` 增加 `applyAppearance(resolvedStyle)`，让 `setValue()` 和布局刷新均读取注入样式。默认样式严格复刻当前视觉。当前 `getSpriteFrame()` / `getBackgroundColor()` 用于技能与合并临时表现，必须与新皮肤一致；下一颗预览也使用同一解析器，不能只替换棋盘内棋子。

`PlayUIState` 只增加必要的外观 ID/版本，不放资源对象或 URL。资源仍由初始化/独立表现入口注入，保留玩法与渲染边界。

## 6. 素材放在哪里

### 6.1 存储分工

| 内容 | 建议位置 | 原因 |
| --- | --- | --- |
| 默认主题/默认方块 | 游戏本地，沿用现有 `assets/images`、Prefab 和场景引用 | 保证首次启动和离线可玩 |
| 外观制作源文件、导入图片 | 客户端仓库 `assets/appearance-bundles/`，设计母版放仓库既有设计目录 | 在 Creator 导入和统一验证，保留可重建来源 |
| 已构建的扩展 Bundle | 静态源站，建议腾讯云 COS + CDN | 按需下载、缓存、版本可回滚，减少业务 API 带宽 |
| 小型目录与权益 | 业务 API；目录可缓存，玩家响应不得公共缓存 | 统一活动配置、授权和环境分流 |
| 缩略图 | 同一静态资源域名下的版本化图片 | 列表不需要下载完整主题 |
| 已下载缓存 | 微信引擎缓存；Web 使用其可用缓存机制 | 缓存可能被系统清除，不作为拥有凭证 |

可先用现有 Ubuntu 的 Nginx 独立静态目录验证下载，再将相同路径迁到对象存储。不要把图片存 MySQL、Base64 塞接口，或经 Node 业务接口逐张转发。生产建议静态域名与业务 API 分离。

### 6.2 目录约定

以下为未来新增目录，不要求迁移现有默认资源：

```text
assets/appearance-bundles/
  theme_forest_v1/          # 一个无脚本的远程 Bundle
    manifest.json
    textures/background.png
  skin_jelly_v1/            # 另一个无脚本的远程 Bundle
    manifest.json
    textures/body.png
    textures/shadow.png
    textures/outline.png
    textures/highlight.png
    textures/crown.png
```

构建后发布完整输出及依赖，而不是把上面的源码 PNG 目录直接当 Bundle 地址。不要把远程 Bundle 放入 `assets/resources/`，也不要让启动场景或默认 Prefab 静态引用远程扩展图。首期每个包自包含，避免不同外观包相互依赖；构建时检查是否产生意外共享依赖或重复打包。

示例 CDN 路径（域名为占位符，尚未配置）：

```text
https://static.example.com/1024/dev/wechat/appearance/r001/theme_forest_v1/
https://static.example.com/1024/dev/web/appearance/r001/theme_forest_v1/
https://static.example.com/1024/prod/wechat/appearance/r001/skin_jelly_v1/
```

开发/正式、微信/Web 构建产物分别发布。一个发布目录不可覆盖；升级创建新 release 路径，并给 Bundle 使用唯一名称。目录记录 `bundleName`、完整 `bundleUrl`、构建生成的 `bundleVersion`、字节数和兼容版本；玩家表只存稳定物品 ID，不存 CDN URL。

静态服务使用 HTTPS；上线前配置微信相应网络合法域名并用真机验证；Web 配置跨域响应。不要依赖开发工具“不校验域名”设置。资源可以公开缓存，下载得到图片不代表账号已获得使用权。

### 6.3 文件与内存预算

建议首期目标（项目预算，不是引擎或平台承诺）：单主题下载 ≤ 1.5 MB、单皮肤 ≤ 500 KB、单缩略图 ≤ 40 KB；超标需评估实际体验。主包遵守仓库 4 MB 上限，必须以真实构建产物核算，不用源码目录大小代替。

PNG 压缩体积不等于显存：1024×2048 的 RGBA8 纹理仅基础像素约 8 MiB，尚未计 mipmap 和其他开销。只保留默认外观、当前外观及一个预览候选，列表缩略图按可见区域加载。

方块首期沿用现有 160×160 透明画布约定，检查 Alpha 有效尺寸，保留 `trim=false` 和相对棋子尺寸布局；背景按常规屏幕、长屏安全区检查裁切。棋盘装饰不能烘焙出固定 5×7 格子，需继续适配合法尺寸。

真正制作/替换 UI 位图时必须先完整阅读 `Skills/cocos-cream-ui-assets/SKILL.md`，执行其像素、Alpha、运行时大小、体积及预览检查。本次只写方案，没有生成或替换素材。

## 7. 如何加载、缓存与切换

### 7.1 加载流程

1. 启动立即显示本地默认外观，登录成功后并行拉取目录与玩家外观快照。
2. 验证目录 schema、平台、客户端版本及 HTTPS 域名白名单；不支持的项目显示不可用或隐藏，不尝试执行远程代码。
3. 用户预览时只下载目标资源；同一 `(环境, 平台, bundleName, version)` 合并重复请求。
4. 装备前准备完整必需资源，不能加载一张就替换一部分。候选加载完成后，确认请求仍为最新、节点仍存活、账号未切换。
5. 进入 loading 后，并行预加载 game 场景和本局需要的外观。建议外观最多等待 5 秒，失败则以默认外观进入；场景预加载失败单独报错，不能伪装为完成。
6. 主题和皮肤独立降级；每种外观自身保持完整。加载中返回首页时释放候选租约，不让迟到回调覆盖新场景。
7. game 创建前固定本局 `effective` 外观。后台下载后来成功也不在落子中途替换，下一次进入时使用。

Cocos 提供 `assetManager.loadBundle` 加载远程包，包内资源再用 `bundle.load` 读取；开启 MD5 Cache 时可以传构建产出的版本值。示意代码，不是完整生产实现：[官方 Bundle 文档](https://docs.cocos.com/creator/3.8/manual/en/asset/bundle.html)。

```ts
import { assetManager, SpriteFrame } from 'cc'

assetManager.loadBundle(entry.bundleUrl, { version: entry.bundleVersion }, (error, bundle) => {
  if (error) {
    rejectCandidate(error)
    return
  }
  bundle.load('textures/body/spriteFrame', SpriteFrame, (loadError, frame) => {
    if (loadError) {
      rejectCandidate(loadError)
      return
    }
    collectCandidateFrame(frame)
  })
})
```

其中 `entry` 来自校验过的目录，两个回调方法由加载器实现。生产实现还须检查取消标记、有效节点、资源引用和错误兜底。`bundleVersion` 是构建配置 hash，不是随意填入的 `1.0.0`。资源路径用正斜杠、相对 Bundle 根目录、不含源文件扩展名；SpriteFrame 子资源按实际导入结果核对。[Bundle API](https://docs.cocos.com/creator/3.8/api/en/class/AssetManager.Bundle)

### 7.2 版本与资源生命周期

- 下载缓存命中仍需校验权益；权益有效也不代表文件已缓存。
- `AppearanceAssetLoader` 对外提供 `acquire()` / `release()` 租约。同一资源被首页预览、棋子或临时特效使用时不能提前释放。
- 替换顺序：完整准备新外观 → 一次性绑定 → 清理旧预览/临时节点 → 释放旧租约。超时回调也要回收其新建资源。
- 共享图层不能被单颗棋子的 `onDestroy()` 直接销毁。退出场景解绑监听，停止 Tween、定时器，销毁动态预览节点。
- Bundle `removeBundle()` 不等价于释放其已加载资源；`releaseAll()` 可能影响外部依赖，仅在确认租约归零、引用已解除后使用。[官方资源释放说明](https://docs.cocos.com/creator/3.8/manual/zh/asset/bundle.html)
- 微信和 Web 的持久缓存能力不同，首期不承诺“下载一次永远离线可用”。不要直接删除引擎用户目录；如后续增加 LRU，只清理本模块确认未占用的外观缓存。
- 远程包只承载已有客户端能够解释的资源和数据。新增组件、脚本或表现语义必须随客户端发布；微信远程脚本受限制。[官方说明](https://docs.cocos.com/creator/3.8/manual/en/asset/bundle.html)

## 8. 服务端模型与一致性

下列是逻辑模型，实施前检查后端现有表，复用已有玩家、幂等和经济流水能力。不要假定这些表已存在。

| 逻辑表 | 关键字段/约束 |
| --- | --- |
| `cosmetic_items` | `item_id` 主键；`kind=theme/skin`、名称、状态、最低客户端版本；状态区分在售、停售、禁用 |
| `cosmetic_releases` | `(item_id, platform, release_id)` 唯一；bundle 名称、URL、构建 hash、manifest schema、资源大小 |
| `cosmetic_offers` | offer ID、ruleVersion、活动时间、领取截止时间、阈值/碎片价格、奖励时长、次数限制 |
| `player_cosmetic_entitlements` | `(player_id,item_id)` 唯一；`permanent`、`expires_at`、更新时间 |
| `player_cosmetic_wallets` | player 主键；fragment balance 非负整数、revision |
| `player_cosmetic_equipment` | player 主键；selected theme/skin、独立递增 appearance revision |
| `cosmetic_grant_ledger` | 来源类型、source ID、player、item、增量、兑换前后状态；业务来源唯一索引 |
| `cosmetic_fragment_ledger` | player、来源 ID、正负 delta、余额、发生时间；来源唯一索引 |
| `cosmetic_requests` | `(player_id,operation_id)` 唯一；请求摘要、状态与响应结果；相同键不同参数拒绝 |
| `verified_game_results` | 可复用成绩表；player、稳定 game ID、审核状态、score、结束时间、活动归属 |

所有外观权益/钱包/装备变更在事务中递增该玩家的 `appearanceRevision`；客户端只接受不旧于当前 revision 的快照，与既有 `cloudRevision` 分开。目录用独立 `catalogVersion`。

### 8.1 永久兑换事务

1. 从登录凭证确定 playerId，不接受客户端指定受益玩家。
2. 按统一顺序锁定该玩家的外观状态行和钱包行，检查 operationId；已完成则重放原结果。
3. 读取并验证 offer、当前规则版本、物品状态、既有永久权益；客户端只提交 offer ID，不提交可信价格。
4. 若客户端所见 `ruleVersion` 已变化，返回 `OFFER_CHANGED`，显示新价格后由用户重新确认，不自动提高扣费。
5. 条件扣余额（余额必须 ≥ 价格），写永久权益、负数碎片流水、权益流水、新 revision 和幂等结果，同事务提交。
6. 超时或断网后用原 operationId 重试；不得换 ID 猜测交易结果。并发不同 ID 兑换同一物品也必须在锁内检查永久权益，保证不重复扣款。

领取限时奖励采用相同事务原则，并额外对 `(player,offer,活动领取周期)` 建唯一约束。客户端 operationId 只能防网络重试，业务唯一键才能防换 ID 重复领。

### 8.2 成绩可信度与对局标识

当前客户端 `recordGameFinished()` 在记录完成时生成 gameId，并上报分数；从客户端代码无法证明服务器具备防作弊能力。给数字加签、加密本地存档或限制阈值都不能证明成绩真实。

建议奖励对局新增服务器签发的 `runId`，开局时绑定玩家、游戏规则版本和开始时间，写入 `OngoingGameSession` 纯数据快照。续局沿用 runId，完成结算只有一份记录；不能在重试或返回首页时生成新 runId。

首期最低校验：合法规则版本、合理时长、分数/最大方块边界、提交频率、对局状态和重复结束；异常记录待审核，不发奖励。该层只能降低滥用，不能完全证明成绩。价值较高的活动需增加确定性随机种子、输入操作序列和服务端重放，明确额外开发成本。

建议首期奖励只接受在线开局并在活动期间完成、及时提交审核的对局；纯离线或旧客户端无 runId 的成绩仍可保留普通进度，但不直接获得装扮奖励。若允许离线奖励，必须另行定义可信时间与重放方案，不能凭客户端 `occurredAt` 跨天补领。

`game_finished` 同步被确认仅表示数据已接收，奖励资格必须等待 `verificationStatus=accepted`。优先在现有成绩处理后复用审核结果发碎片，避免再开一条独立成绩上报通道。旧 outbox 的 200 条裁剪不能承担重要未确认交易；领取、兑换和装备的待确认 operationId 存单独小型持久记录，完成后删除。

## 9. 建议接口契约

以下均为新增设计，沿用 `GameApiClient` 的 `{ data: ... }` / `{ error: ... }` 包装。开发请求基址为 `https://leyian.online/dev/v1`，正式为 `https://leyian.online/v1`。

| 方法与路径 | 请求 | 返回要点 |
| --- | --- | --- |
| `GET /cosmetics/catalog?platform=wechat&clientVersion=...` | 平台、客户端版本 | catalogVersion、serverTime、items、offers、releases |
| `GET /me/cosmetics` | 登录凭证 | serverTime、appearanceRevision、碎片、权益、装备、活动进度/可领状态 |
| `POST /me/cosmetics/claims` | operationId、offerId、ruleVersion | 完整玩家外观快照、grantId |
| `POST /me/cosmetics/exchanges` | operationId、offerId、ruleVersion | 完整快照、兑换结果 |
| `PATCH /me/cosmetics/equipment` | operationId、expectedRevision、slot、itemId | 完整快照；并发冲突返回最新 revision |

`platform=web` 使用对应 Web 产物。每次修改返回完整的小型外观快照，避免客户端分别加余额、加权益造成部分更新。

示例玩家快照：

```json
{
  "data": {
    "serverTime": "2026-10-09T08:00:00Z",
    "appearanceRevision": 12,
    "fragments": 35,
    "selectedThemeId": "theme_forest",
    "selectedSkinId": "skin_default",
    "entitlements": [
      { "itemId": "theme_forest", "permanent": false, "expiresAt": "2026-10-16T08:00:00Z" },
      { "itemId": "skin_default", "permanent": true, "expiresAt": null }
    ],
    "claimableOfferIds": []
  }
}
```

物品发布记录示意字段：`itemId=theme_forest`、`platform=wechat`、`releaseId=r001`、`bundleName=theme_forest_v1`、`bundleUrl=版本目录`、`bundleVersion=构建hash`、`manifestSchema=1`、`minClientVersion=支持此描述的版本`、`downloadBytes=实际产物体积`。版本比较应解析版本段，不用字符串字典序。

建议业务错误：`SCORE_NOT_QUALIFIED`、`ALREADY_CLAIMED`、`ALREADY_OWNED`、`INSUFFICIENT_FRAGMENTS`、`OFFER_CHANGED`、`OFFER_CLOSED`、`ENTITLEMENT_EXPIRED`、`ITEM_DISABLED`、`REVISION_CONFLICT`。沿用既有未登录/超时错误处理。

## 10. 时间、离线、账号与续局

- 同一前台运行内以服务器时间为基线，加单调时钟 elapsed 估算倒计时，不能用设备当前日期直接续命。
- 回到前台、进入新局、恢复存档和装备前刷新权益；限时权益校验请求失败则保守回退默认项。倒计时变负只改变展示，不在客户端删除服务器记录。
- 冷启动离线时，已缓存的永久权益及资源可继续用于该账号的外观展示；限时权益需联网确认。永久缓存只是客户端便利，不是服务器可接受的授权证明。
- 已在前台进行的一局到期或临时断网，保留本局显示；跨场景续局或从后台恢复是新的校验入口。明确不以“一直保存续局”无限延长租期。
- 游客可使用默认外观和预览，领取/兑换需登录。游客本地余额、最高分不直接导入永久权益。
- 存储键采用 `getOnlineStorageKey('appearance-v1') + ':' + playerId`；退出登录立即清理内存权益、装备候选与未完成回调。资源文件可按环境共享缓存，权益绝不跨账号共享。
- 用户恢复旧存档时新增字段均可选；缺失则取当前合法装备/默认值。资源版本已下线时可改用兼容版本或默认图，不阻止恢复棋盘。
- 多设备冲突按服务端 revision 解决；装备失败后刷新并提示重试，不用客户端时间判定“最后操作”。

## 12. 实施拆分与验收

### 阶段一：本地外观解耦

交付默认描述、类型、皮肤注入、主题 token 接口与一个开发用候选外观。优先证明更换表现不会影响玩法。

主要文件：新增 `appearance/AppearanceTypes.ts`、`DefaultAppearance.ts`、`AppearanceRuntime.ts`；修改 `PieceController.ts`、`PlayUIController.ts`、`PlayController.ts`。保留现有 Prefab 属性及资源引用。

验收：默认画面无回归，数字/下一颗/技能碎片一致，5×7 及其他合法尺寸正确，普通落子与合并不触发网络加载。

### 阶段二：服务端权益闭环

交付目录、背包、领取、碎片兑换、装备 API 和事务；补齐稳定 runId、成绩审核状态和来源唯一约束。后端具体迁移文件名待核查独立仓库后确定。

客户端新增 Store、Service、API 方法；接首页入口。先用本地资源验证 7 天、永久和失败重试，不等待全部美术完成。

验收：重复领取不续期，并发兑换只扣一次；已永久拥有不扣；修改本地时间不延长；开发/正式及两账号数据隔离。

### 阶段三：远程资源闭环

交付 AssetLoader、一个远程主题与一个远程皮肤、缩略图与目录版本；接入 LoadingSceneController 和首页预览。

验收：首次下载、二次缓存、网络超时、404、错误 hash、版本不兼容、内存释放、快速切换候选和切场景均能正确处理。主包体积按构建实测。

### 阶段四：真机与活动调参

交付最终主题卡片、兑换弹窗、倒计时、错误提示和运营配置；开发环境完成下表后再准备上线评审。

| 验收场景 | 预期 |
| --- | --- |
| 分数差 1 分、恰好达标、超过阈值 | 仅通过审核且达标的局提供领取资格 |
| 同一个成绩/领取请求重复发送 | 只有一份奖励/碎片流水 |
| 请求已提交但客户端超时 | 用原 operationId 重试得到原结果，无二次扣款 |
| 两设备同时兑换、同时装备 | 余额不为负，权益不重复扣款，装备 revision 可收敛 |
| 活动结束、配置改价、限时转永久 | 遵守领取窗口；改价重新确认；永久不再倒计时 |
| 到期瞬间、前后台切换、改设备时间 | 当前前台局不闪变，恢复/新局重新校验 |
| 资源下载失败、缓存被清理、旧版本回滚 | 权益保留；默认外观可玩；重试不重复购买 |
| 连续切换预览、退出弹窗、切换账号 | 迟到回调不覆盖当前界面，不泄漏旧账号状态 |
| 生成、选列/快速下落、合并连锁、重力 | 样式切换不改变数值、坐标、速度与结算 |
| 暂停/恢复、炸弹、锤子、交换、续局、结束 | 冻结与动画时序不变，临时表现使用正确皮肤 |
| 常规屏幕/长屏、多个合法棋盘尺寸 | 安全区和命中一致，无硬编码格子背景错位 |
| 低端微信真机反复进入/退出装扮 | 无持续内存增长；主包、下载与帧率达到实测目标 |

后端应新增真实数据库事务/并发/幂等测试；客户端仓库目前无自动化测试与 CLI 构建，使用 Creator 和微信开发者工具进行功能与引用检查。不要用“TypeScript 看起来能编译”代替真机验收。
