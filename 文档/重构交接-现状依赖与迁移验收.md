# 重构交接：现状依赖与迁移验收

日期：2026-10-23。配套主文档：[重构设计-场景组合与外观解耦](重构设计-场景组合与外观解耦.md)。

## 1. 交接范围与证据边界

**最高验收约束：重构前后玩法与表现不变。** 只能重组内部实现，不能借解耦改变布局、动画、素材、声音、交互、数值、流程或错误回退。后文“补全、统一、提取”均受此约束；如需修复已有问题或新增功能，单独列项等待用户授权，不与结构迁移混做。

本文中的主题扩展是未来架构能力，不是本轮功能交付。所有新外观和新场景表现仅可用于隔离测试或设计说明，不接入正式用户流程。

用户本次只要求深读项目并设计方案。本文不是实施授权，不包含代码、场景、Prefab、图片、元数据、构建产物或服务器变更。后续模型接到实施任务后，先重新检查 AGENTS.md、Git 差异和对应代码，再按阶段执行。

此次深入检查了三场景入口、PlayController 的初始化/续局/技能/结算/退出调用链、方块表现、棋盘配置、经济同步、账号存储、资料与头像、超越目标、平台广告与更新逻辑；检查了其他弹窗和平台模块的导入、资源入口及生命周期关键段。解析了三个 scene 的节点结构，列举了 Prefab，检查了构建配置和专项验证脚本。不是对全仓所有方法逐行审计，不承诺不存在遗漏或运行缺陷。

所有结论属于静态检查。未执行 Creator、微信开发者工具、真机、专项脚本或后端验证；独立服务端实现仍未核实。代码中的已有注释或旧文档不能代替当前实现证据。

优先级：用户明确要求与 AGENTS.md → 本次架构及交接约束 → 具体阶段计划。发现冲突时说明并修订方案，不能以重构为由静默改玩法或产品规则。

## 3. 必须覆盖的入口矩阵

| 入口 | 当前事实 | 外观/重构接入要求 |
| --- | --- | --- |
| 首页新局 | consumeEnergy 成功 → beginNewGame → loading 或 game 兜底 | 消费只发生一次；资源重试不能再扣体力；外观失败可 Base 回退 |
| 首页续局 | enterOngoingGameScene 直接进入 game，绕过 loading | 在首页转场准备或 game 启动门控中准备外观；不强制新增 loading，不重复扣费 |
| Creator 直接预览 game | 无会话时按 Inspector 尺寸 beginNewGame | 无外观交接槽时合法启动 Base，不依赖首页初始化过单例 |
| 直接预览 loading | targetSceneName 决定目标 | 可以准备默认外观，最低展示时间保留，失败不假装 100% 成功 |
| 游戏内 restartGame | 原场景异步扣体力、清棋盘、重置、再生成 | 不经过 onLoad 或 loading；外观按新局边界准备，锁住输入，失败不重复消费 |
| 暂停返回首页 | 保存纯数据快照，再清理棋子/特效并切场景 | 保存必须在清理前；恢复后技能广告次数及当前落子位置仍属于原局 |
| 结算返回首页 | finishGame，不保存续局 | 与暂停返回共用安全清理，但不能误保存已结束对局 |
| 后台恢复 | 多个平台/同步/表现模块各有恢复逻辑 | 不把恢复等同重新开局；新增外观权益校验不能触发扣体力或重复结算 |

建议提取小型、明确的“进入对局准备”操作供以上入口复用，不引入全局导航框架。正常 loading 转场使用主文档租约交接；直达入口在本地取得租约；原场景重开在新局开始前换租约。每条分支都记录当前所有者。

现有转场失败的恢复策略并不完整。实施前应分别确定：扣体力已成功但切场景失败时保留何种待进入状态、重试如何复用它、快照何时消费。默认不自动退款、不再扣款、不把外观加载失败当成玩法失败；退款或持久化转场意图属于另行确认的行为变更。

## 4. 玩法与经济行为基线

1. 尺寸当前支持列 1～6、行 1～7；默认 5×7。包含 3×7 和边界尺寸的验证，不能只测试默认盘面。
2. 先应用本局 BoardConfig，再 resetBoard、创建 BoardGeometry 和 UI。不能让 UI 初始化后才修改棋盘大小。
3. 当前下落棋子不在 board 中，清理和快照都要单独处理。当前分数不包含正在下落的棋子。
4. 落地局部连锁后进入重力和全盘同值四向连通扫描，稳定后才生成下一颗。提取动画不能提前解除 isResolving。
5. 技能选中冻结下落但不是暂停弹窗；无效交换回弹或取消不扣次数。广告准备也有独立冻结状态。
6. 库存每技能每局最多使用一次；广告另赠本局机会，ready 优先消费。广告观看成功不自动施放，不直接增加持久库存。
7. skillAdRewards、usedSkillsThisGame 都进入续局快照；旧快照缺字段需兼容，重开才重置。
8. 广告必须完整观看关闭才算 completed；Web unsupported 不得模拟发奖。旧广告回调由 skillAdRequestVersion 阻断，不能带进新局。
9. 新手引导仅用于无快照且未完成引导的新局；高亮列触摸才放行。引导遮罩和普通触摸的传播顺序不能变。
10. endGame 以结束标记防重复；发金币、记录 game_finished、等待本 operationId 的名次回执是不同步骤。移入新类不能重复调用旧入口。
11. 结算名次等待当前为 3 秒，迟到结果由 settlementGeneration 抑制；不能拿上一批同步的名次替代本局。
12. 重开等待体力回执时禁止重复操作；失败恢复原暂停状态。局部组件不可自行绕开消费流程。

当前分数与金币、广告规则是保留基线，不代表经过产品重新确认。重构不得借优化之名改数值和奖励时机。

## 5. 联网、账号与缓存：容易遗漏的边界

- 游客启动不主动 wx.login；已有凭证走 restore。排行榜/个人中心由用户点击后经隐私授权、登录、同步、资料请求进入。不要为了统一初始化强制登录。
- PlayerCloudSyncStore.activate 由首页和游戏订阅；最后一个订阅释放后清定时器及网络监听。场景拆成多个组件不能无意重复激活服务。
- 体力以服务端时间及单调时钟为基线；进入后台作废时间基线，恢复校准。倒计时归零不由 UI 直接加体力。
- 同步包含 confirmed 快照 + pending 操作重放，接受/拒绝/重复回执均有处理。重构不能把服务器响应直接覆盖当前显示后丢失在途新增操作。
- 开局 startIntent 持久保存原 operationId；401 恢复和网络重试不能另建消费 ID。账号切换后的异步结果必须失效。
- 当前 outbox 的 200 条裁剪只用于游客队列，已登录队列不按此分支裁剪。原主题方案写“队列上限 200”过于概括；实施以当前代码为准，重要主题交易仍需独立待确认记录。
- 初次游客导入与正常增量同步不同；一次最多处理三批、每批操作最多 100 条。不要把这些机制混入场景 render。
- 环境由 API 地址隔离，正式保留旧存储键；首个账号可迁移旧环境存档，后续账号不能再次继承。新增模块须复用既有隔离规则，不能只按主题 ID 缓存权益。
- OngoingGameSession 是进程内对象，不是已落盘存档。同步请求目前发送 ongoingGame:null；不能因云快照类型有该字段就宣称支持云续局。
- OvertakeRivalStore.begin/end 与对局绑定，缓存按账号；resolveOvertake 不发请求，updateScore 负责协调。保留严格超越和已有退避/次数上限。
- PlayerProfileStore 更新串行、带 revision/generation；保留内置头像与微信头像兼容。头像渲染按位置持有引用，多个 UI 共享纹理不能互相销毁。
- 微信头像走原生 Image，Web 走引擎远程图片加载；不能为统一资产加载而替换该平台差异。主题离线素材与用户远程头像是两种资源域。

以上为客户端事实；不据此认定服务器已经具备成绩审核、主题权益或强防作弊。

## 6. 资源、序列化与布局交接

### 6.1 已核对的场景结构

- home.scene：Main 下的 StartPageOverlay/PageCard/HomepageArtwork 及既有首页子节点；含序列化秋千结构和 EnergyBar 引用。
- loading.scene：Main、Logo 等少量节点；当前主体 UI 在运行时创建，不能误以为已有完整静态层级可直接绑定。
- game.scene：Main 下有 board、五个静态 column 占位、PieceLayer、FxLayer、Status、SkillsController、FeedbackLayer、OverlayLayer；覆盖层含 PauseOverlay 与旧 GameOverOverlay 节点。
- 当前代码会在旧结算挂点关闭旧子节点，再加载 Settlement/SettlementPopup；不能只看 scene 就删除“没用的旧节点”，也不能同时显示两套结算。

目录/资源契约至少包括：

```text
assets/prefab/piece.prefab
assets/prefab/EnergyBar.prefab
assets/prefab/CoinBar.prefab
assets/prefab/DailyRewardPopup.prefab
assets/prefab/SkillShopPopup.prefab
assets/resources/base/Gameplay/ScoreTargetHUD.prefab
assets/resources/base/Settlement/SettlementPopup.prefab
assets/resources/base/Profile/ProfilePopup.prefab
assets/resources/base/Leaderboard/LeaderboardPopup.prefab
```

这些是已列出的入口，不是全部传递依赖。实施每阶段须记录受影响脚本的 @ccclass、@property 名称和类型、脚本 .meta UUID、场景/Prefab 绑定、动态路径、硬编码 UUID、子资源类型及路径。新 helper 可先用普通 TypeScript 类；不必为拆方法给场景加大量序列化组件。

### 6.2 布局与输入

**节点管理要求：固定结构交给 Creator 静态层级，脚本不再承担整页搭建。** 首页、加载页、HUD、设置和弹窗中现有运行时构建代码必须进入迁移清单。对每类节点记录目标 Scene/Prefab、原父节点与顺序、组件参数、序列化绑定、事件和动画目标，按界面逐项迁移并验证等价。

动态实例化与运行时搭建结构要区分：棋子、列表项或按需弹窗可以 instantiate 已编辑的 Prefab；其固定内部结构由编辑器维护。程序粒子和棋盘装饰等有明确理由的动态节点可保留，不应为追求零动态节点破坏玩法和表现。棋盘装饰唯一绘制入口的项目规则仍优先。

加载页目前主要由代码创建，因此静态化属于需要明确核对场景绑定的迁移工作，不是简单删 ensure 方法。设置及结算的旧节点/新版 Prefab 并存路径也要分别确认，不能误恢复旧 UI。

首页、加载页、游戏页的设计尺寸和裁切策略不完全相同，不能直接统一成一个全局缩放系数。共享的应是安全区信息来源及必要换算函数，各场景保留具体布局决策。

保留首帧后补一次布局的路径。棋盘、特效层、引导高亮必须使用一致坐标；弹窗、头像原生按钮、遮罩的触摸阻断也需回归。新增纯装饰不得拦截棋盘输入或遮住覆盖层。

### 6.3 引擎启动页与加载场景不同

tools/wechat-startup-page 是引擎启动前页面；settings 的 splash 又是构建配置，二者都不是 loading.scene。不要把场景主题机制自动扩大到原生首屏。

现有安装脚本会处理 resources Bundle 的微信分包归属，并校验产物。主题 Bundle 设计必须考虑此已有流程：不可未经验证改 resources 名称、路径或产物结构；主题间共享依赖以实际构建为准。本次不执行构建后处理，不修改该脚本。

## 7. 生命周期与并发任务清单

| 所有者 | 必须收口的任务 |
| --- | --- |
| 场景入口 | 订阅释放、切场景延迟、登录/同步后续 UI 回调、外观候选租约 |
| 对局 | 合并/重力/技能等待、广告请求、重开体力请求、结算名次超时及超越目标会话 |
| 视图/弹窗 | 按下 Tween、入退场动画、头像请求、分页与资源加载、原生资料按钮 |
| 装饰 | update、定时器、独立音效、局部触摸和内部节点 |
| 进程服务 | 同步定时器按订阅启停；更新监听进程级保留，不能按场景重复注册 |

注意：当前某些控制器在自身 onDestroy 中复用自身 onDisable。迁移时建议提取幂等公共清理函数，避免混淆暂停和永久释放；不能手动调用其他组件生命周期方法。GameAudioManager 当前没有统一 dispose 入口，提取资源所有权时需同时审视其迟到音频加载与音源生命周期，不能只清视觉资源。

所有等待动画/定时器的 Promise 都需要完成与取消出口。停止 Tween 或 unscheduleAllCallbacks 可能令旧等待永远不返回；接手模型需逐个检查 animateMove、waitSeconds、技能动画及 Promise.all 分支，不只在入口加 isValid。

任务代次分开：场景代次防离场，局代次防重开，账号代次防串号，视图可见代次防关窗后回显。不要用一个全局版本号让无关请求互相取消。

| 工作包 | 交付 | 必须检查的非主路径 |

每个工作包交付必须列出：修改职责、保留接口、旧实现是否删除、未删除原因、验证结果、未执行项。不允许只写“已解耦”。

### 9.1 行为等价放行门槛

实施前为受影响功能保存基线：输入与初始状态、关键数值、截图、操作录像、动画与声音触发顺序。实施后使用同一条件对比。网络和随机因素通过测试夹具控制，不修改发布版规则。

验收分别记录“玩法等价”和“表现等价”。前者检查盘面、分数、消费、奖励、快照、请求次数及状态转换；后者检查像素布局、显示内容、层级、命中、动画路径/时长/缓动、粒子、声音、按下反馈及加载过程。不能只证明最终盘面相同，也不能只证明静态截图相同。

原表现中的有意差异必须保留，例如预览与完整棋子的图层不同、临时碎片只显示主体。发现原有缺陷先登记，不在本轮自动纠正。缺少运行条件时标为未验证，不据此宣称可合并或等价已通过。

若出现玩家可感知差异，回退相关工作包或修正到原行为再继续；不得以“效果更好”“实现更统一”“性能更好”替代用户授权。

阶段清账至少包括：

- [ ] 新旧状态更新没有双写，奖励/扣费/监听没有执行两次。
- [ ] 已迁出的规则没有继续留在旧控制器中充当另一份默认实现。
- [ ] 固定界面已在 Scene/Prefab 层级中可编辑；保留的动态创建有用途与所有者，不存在换文件后继续整页造节点的情况。
- [ ] retained 门面和兼容代码有明确调用者，不无限保留空转发层。
- [ ] 序列化引用、动态路径、旧导出路径经过核对；PlayController 对 OngoingGameSession 的兼容 re-export 不能直接删除。
- [ ] 首页新局、续局直达、场内重开、直接预览、两个返回入口均有结果记录。
- [ ] 设置/结算/HUD/资料/排行榜的销毁链覆盖，而非只验证一个关闭按钮。
- [ ] 同步和头像的账号隔离、存储失败、断网、401/409、迟到回调有对应记录。
- [ ] 样式、场景专用能力、玩法与经济规则的边界均未因新模块而退化。
- [ ] 已知限制有编号、原因、后续条件，未把未验证项目写成通过。

## 10. 明确保留与待验证项

| 编号 | 项目 | 处理原则 |
