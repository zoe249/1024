# 实现方案：微信头像与内置头像共存

日期：2026-10-03  
状态：客户端和服务端代码已实现；验证及上线状态见第 11 节

## 1. 目标与范围

参照用户提供的消消乐截图，在当前个人中心的头像列表中加入一个固定的微信头像入口：

- 第一项始终是“微信头像”。已授权且获取到头像时展示用户头像；确认未授权时，在格子内显示“暂未授权”。
- 后续保留 11 个内置头像，玩家可自由切换；总计 12 个选项。
- 选用结果统一用于个人中心顶部、首页入口和排行榜。
- 微信返回的头像 URL 直接用于远程图片加载，不把微信头像编入内置头像编号。

参考图用于确定“首项为微信头像、其余为游戏头像”的交互关系。本期沿用数字花园现有个人中心风格，不扩展截图中的头像框、装扮页签、游戏记录和收集进度。

设计以用户恢复后的原版代码为基础，保留内置头像，与新微信头像入口共存。当前实施结果见第 11 节。

## 3. 界面与交互

### 3.1 列表排列

保留现有头像区和 4 列 × 3 行布局：第一格为微信头像，其余 11 格为内置头像，总计 12 项。本方案默认从可选列表中移除末尾的浣熊（原编号 11），保留兔子至刺猬（原编号 0～10），无需新增一行或滚动列表。

```text
┌──────────┬──────────┬──────────┬──────────┐
│ 微信头像 │ 兔子 #0  │ 狐狸 #1  │ 蓝鸟 #2  │
├──────────┼──────────┼──────────┼──────────┤
│ 橘猫 #3  │ 小鸡 #4  │ 乌龟 #5  │ 小鹿 #6  │
├──────────┼──────────┼──────────┼──────────┤
│ 羊驼 #7  │ 松鼠 #8  │ 青蛙 #9  │ 刺猬 #10 │
└──────────┴──────────┴──────────┴──────────┘
```

图中的编号只用于说明数据映射，实际界面不显示编号。微信项使用小型“微信”文字标识；已选中时复用现有选中效果。占位底色和文字可由现有 Graphics、Label 实现，无需新增 PNG。

授权未完成时，“暂未授权”位于第一格内部，而不是整个头像区或顶部当前头像上。顶部继续显示玩家当前使用的内置头像。

### 3.2 第一项的显示状态

| 状态 | 第一格显示 | 点击行为 |
| --- | --- | --- |
| 正在查询授权 | 占位底色、“读取中…” | 等待查询，避免重复操作 |
| 已确认未授权 | 占位底色、“暂未授权” | 通过原生用户信息按钮请求授权 |
| 授权状态查询失败 | 占位底色、“点击获取” | 重试查询与获取；不误判为未授权 |
| 已授权，正在读取资料或图片 | 占位底色、“加载中…” | 读取期间去重 |
| 已授权，有有效 URL 且图片加载成功 | 用户头像、“微信”标识 | 保存为当前头像 |
| 已授权，但未返回有效 URL | 占位底色、“点击重试” | 再次读取资料 |
| URL 有效，但图片下载失败 | 占位底色、“点击重试” | 重试图片加载，不重复申请授权 |
| 非微信预览环境 | 占位底色、“暂未授权” | 提示“请在微信小游戏中使用微信头像” |

获取 URL 是资料读取成功；图片下载成功是显示成功；服务端确认才是保存成功。这三个结果分别处理。

### 3.3 首次授权并选用

1. 玩家点击第一格，原生透明按钮的点击区域仅覆盖这一格。
2. 微信返回用户资料，读取 `userInfo.avatarUrl`；结构化字段缺失时再尝试解析 `rawData`。
3. 校验 URL，并加载图片供第一格预览。昵称只作为平台读取结果，不在这一步自动保存。
4. 本次点击代表选用微信头像：提交头像类型和 URL，显示保存中的状态，阻止并发切换。
5. 服务端保存并返回完整资料；确认返回的头像类型和 URL 与本次请求一致后，再更新顶部头像、首页头像和选中标记，提示“头像已保存”。
6. 授权取消、读取失败或保存失败时，保持原头像和原选中状态。

授权成功但保存失败时，第一格仍可展示已获取的用户头像，便于点击重试；不得把这项标记为已选用。

### 3.4 切换与刷新

- 点击内置头像：提交内置类型及其原编号，服务端确认后更新显示。
- 已授权但选用了内置头像：第一格继续展示微信头像，选中标记留在内置项上。
- 打开面板或读取已授权资料：只更新第一格可展示的内容，不自动切换当前头像，不自动提交资料。
- 已选用微信头像时再次点击第一格：主动重新获取资料并刷新头像。URL 未变化时复用图片；URL 变化时保存新 URL。
- 微信头像的授权和选用不修改昵称。现有昵称入口继续负责“同步微信昵称”，但需移除适配器读取成功即自动保存的耦合，避免两个入口互相触发保存。
- 本机明确查询到授权已撤销：第一格恢复“暂未授权”。若服务端当前选择仍为微信头像，本机当前头像使用默认内置头像兜底，保留原存储选择，不自动写库；其他设备和排行榜的存储记录待玩家重新授权或主动切换时更新。

## 4. 数据设计：显示位置与头像身份分开

### 4.1 保留已有编号

不得把微信头像插入 `PLAYER_AVATARS` 数组，也不得重排已有编号。可选内置头像为兔子 0、狐狸 1……刺猬 10，共 11 项。原编号 11 的浣熊退出可选列表，资源映射仅用于兼容旧资料，避免旧玩家头像被静默改为其他动物。

界面选项使用有明确身份的结构，而不是直接把格子下标作为数据库编号：

```ts
type AvatarOption =
  | { kind: 'wechat' }
  | { kind: 'builtin'; avatarIndex: number }

// 原资源映射保留；可选列表仅包含编号 0～10。
const SELECTABLE_BUILTIN_AVATAR_INDICES = Array.from({ length: 11 }, (_, index) => index)
const options: AvatarOption[] = [
  { kind: 'wechat' },
  ...SELECTABLE_BUILTIN_AVATAR_INDICES.map(avatarIndex => ({ kind: 'builtin' as const, avatarIndex }))
]
```

点击第二格提交 `avatarIndex: 0`。不得提交显示位置 `1`，也不使用 `-1` 或 `12` 作为微信头像的特殊编号。

### 4.2 服务端持久化字段

```ts
type AvatarType = 'builtin' | 'wechat'

type PlayerAvatarProfile = {
  avatarType: AvatarType
  avatarIndex: number
  wechatAvatarUrl: string
}
```

- `avatarType`：玩家当前选择的头像来源。
- `avatarIndex`：内置头像编号；使用微信头像时保留之前的内置编号，作为显示兜底。
- `wechatAvatarUrl`：最近一次成功保存的微信头像 URL；无记录时为空字符串。切回内置头像时不清空。

旧数据迁移为 `avatarType = 'builtin'`、`wechatAvatarUrl = ''`，原 `avatarIndex` 不变。旧资料若为浣熊 11，顶部、首页和排行榜继续兼容显示，但列表不增加第 13 项，也不错误选中某个现有格子；玩家主动换头像后按新选择保存。保留旧资源及映射，不删除其 `.meta`。

### 4.3 授权和加载状态仅属于客户端

客户端单独维护 `unknown / loading / unauthorized / authorized / unavailable` 等平台读取状态，以及图片加载、资料保存状态。当前读取到的 URL 与已保存 URL 分开存放。

这些状态不写进玩家表。服务端有 URL 不等于本机仍有资料授权；反过来，本机已授权也不等于玩家已选择微信头像。业务凭证快照不增加头像或微信用户资料字段。

## 5. 资料与排行榜接口

### 5.1 资料响应

`GET /v1/profile` 和 `PATCH /v1/profile` 的资料对象增加 `avatarType`、`wechatAvatarUrl`，保留所有原字段。这里仅展示头像部分，响应仍使用项目现有封装：

```json
{
  "avatarType": "wechat",
  "avatarIndex": 3,
  "wechatAvatarUrl": "https://头像服务域名/用户头像地址"
}
```

客户端内部不能只替换 DTO 类型便假定接口已支持。微信头像保存成功必须满足：HTTP 成功、字段齐全、返回 `avatarType = 'wechat'`，并且返回的 URL 与提交 URL 一致。

### 5.2 更新请求

选用微信头像：

```json
{
  "avatarType": "wechat",
  "wechatAvatarUrl": "https://头像服务域名/用户头像地址"
}
```

服务端原子保存类型与 URL，保留原内置编号。切回内置头像：

```json
{
  "avatarType": "builtin",
  "avatarIndex": 3
}
```

保留 `displayName` 的现有独立更新方式。头像操作不带 `displayName`，昵称操作不带头像字段。

校验规则：

- 类型只能为 `builtin` 或 `wechat`；新客户端可选内置编号仅为整数 0～10。编号 11 只供旧资料和旧客户端兼容，不加入新列表。
- 选用微信头像时必须提交有效的 HTTPS URL，建议最大长度 2048；保留查询参数，不根据是否带图片后缀判断有效性。
- 不接受本机临时文件地址作为云端头像 URL。若真机实际返回临时路径，应另行设计上传流程，不能直接保存该路径。
- 服务端仅保存 URL，本期不下载、转存或代理图片；客户端通过现有业务凭证更新自己的资料。
- 部分字段更新不清空其他资料。保存和响应从同一最终资料生成，避免类型与 URL 不一致。

### 5.3 排行榜响应

`GET /v1/leaderboard` 的每个榜单条目及 `self` 都返回相同的三个头像字段。排行榜渲染器按类型解析：

- `builtin`：按原编号加载内置资源。
- `wechat` 且 URL 有效：加载远程图片。
- 数据不完整或图片加载失败：使用该条目的内置编号兜底；不改变排名、昵称和分数。

保存头像后，使本地缓存的个人资料和排行榜展示数据失效或更新；下次开榜重新读取，避免头像切换后仍显示旧缓存。

### 5.4 兼容策略

- 新客户端读取旧响应时，将缺失的类型按 `builtin` 处理，URL 按空字符串处理；旧内置头像正常显示。
- 未确认服务端支持新字段时，不提交微信头像选择，明确提示“微信头像暂不可保存”，不得假报成功。
- 新服务端收到旧客户端仅含 `avatarIndex` 的请求时，按选用内置头像处理，并保留已保存的微信 URL。
- 新服务端仍返回原编号字段。但旧客户端无法显示微信头像，只能展示保留的内置头像；这是旧版本的兼容限制。

## 6. 客户端职责划分

| 模块 | 计划职责 |
| --- | --- |
| `AvatarCatalog.ts` | 保留原资源编号映射；生成 1 个微信项和 11 个可选内置项 |
| `WechatNicknameAdapter.ts` | 扩展用户资料读取结果为昵称和头像 URL；查询授权、管理原生按钮；不调用业务接口 |
| `ProfilePopupController.ts` | 渲染 12 个选项及状态，通过回调表达授权获取、选用和刷新意图 |
| `HomeSceneController.ts` | 协调平台读取、资料保存和各界面更新；区分静默读取与用户主动提交 |
| `PlayerProfileStore.ts` | 规范化纯数据，保存服务端确认后的资料；串行处理更新，过期的读响应不能覆盖新保存结果 |
| `GameApiClient.ts` | 扩展请求和响应契约，保留现有业务凭证和错误处理 |
| 拟新增 `PlayerAvatarRenderer.ts` | 统一本地/远程头像显示、异步回调校验和资源释放 |
| `StartPageController.ts` | 使用统一头像描述显示首页当前头像 |
| `LeaderboardPopupController.ts` | 使用同一渲染器显示条目及当前玩家头像 |

纯数据快照不持有 Node、Sprite 或纹理。微信原生按钮由平台适配器管理，远程纹理由渲染层管理。

### 6.1 微信能力接入

拟复用当前小游戏代码里的 `wx.getSetting`、`wx.getUserInfo`、`wx.createUserInfoButton`，扩展读取 `avatarUrl`。授权入口依赖用户点击，打开个人中心只做查询和已授权资料读取。

原生按钮必须在面板入场动画结束后定位，并在尺寸变化时更新。面板关闭、切场景、组件销毁或该入口不应响应时，解绑回调并隐藏、销毁原生按钮。请求使用代次标记，旧回调不得影响重新打开的面板。

昵称入口与头像入口可以复用读取能力，但各自只提交用户明确触发的字段。不要记录完整 `userInfo`、`rawData` 或包含签名信息的 URL 日志。

### 6.2 远程头像加载

微信小游戏中的头像通过 `wx.createImage()` 直接读取原始 URL，再构造 `ImageAsset`、`Texture2D` 与 `SpriteFrame`，不经过 `wx.downloadFile`。Web 预览通过 `assetManager.loadRemote<ImageAsset>` 获取；无后缀 URL 需要明确指定图片扩展类型。Web 预览存在 CORS 限制，微信真机效果需单独验证。[Cocos Creator 3.8 动态资源加载说明](https://docs.cocos.com/creator/3.8/manual/zh/asset/dynamic-load-resources.html)

实现要求：

- 同一 URL 的在途请求与图片复用，避免首页、个人中心和排行榜重复下载；使用有限缓存和明确的引用释放规则。
- 头像请求带目标身份和请求代次校验，快速切换时旧图片不能覆盖新头像；排行榜行复用时也必须校验。
- 加载中或失败先显示内置兜底；图片失败不阻塞弹窗打开，不改变已保存的头像类型。
- 玩家主动选用微信头像前先完成图片预览，避免立即保存一个本机无法展示的地址；其他设备加载失败仍能兜底。
- 按现有圆形头像区域裁剪照片，保持比例，避免拉伸。当前引擎裁剪配置中的 Mask 未启用，实施时需在 Creator 中启用并验证实际预览。
- 离开界面释放使用引用，销毁自建 SpriteFrame、Texture2D；不得销毁其他显示节点仍在使用的共享资源。
- 图片失败时允许用户点击重试，不持续自动轮询，也不无限缓存不同用户的头像。

## 7. 错误提示与一致性

| 失败阶段 | 推荐提示 | 保留内容 |
| --- | --- | --- |
| 玩家取消头像资料授权 | “已取消授权” | 原头像与原选中项 |
| 隐私确认未完成 | 复用当前隐私提示 | 原头像与原选中项 |
| 微信未返回有效头像 URL | “未获取到微信头像，请重试” | 原头像；可继续选内置项 |
| 远程图片失败 | 格内“点击重试”；点击后仍失败提示“头像加载失败” | 已保存资料不变 |
| 保存接口网络失败 | “头像保存失败，请重试” | 原选中项；已获取的微信预览 |
| 服务端未支持新字段 | “微信头像暂不可保存” | 原选中项；禁止显示保存成功 |
| 保存响应类型或 URL 不符合请求 | “头像未保存成功，请重试” | 原显示；重新读取资料核对 |
| 开发者工具不能返回用户头像 | “请使用微信真机获取头像” | 不把模拟失败当作真实授权取消 |

保存请求超时存在“服务端可能已保存”的情况。重新进入或重试时先核对服务端资料；界面以最终资料为准，不能仅凭本地临时选中状态宣称成功。

## 8. 实施顺序

1. **核对平台能力与服务端接入条件。** 在微信真机确认当前小游戏账号、基础库和隐私配置下实际返回 `avatarUrl`。取得服务端源码与可用连接方式，核对资料表和排行榜查询。此前 Mac 的 SSH 登录未成功，不能把文档中的 Windows 私钥路径当作本机已可用连接。
2. **服务端先支持新契约。** 新增迁移、资料读写和排行榜字段；旧请求仍可处理。通过真实接口确认 URL 能持久化，并在重新读取与排行榜中返回。

### 头像加载路径修正

用户报告 `thirdwx.qlogo.cn` 无法添加到 `downloadFile` 合法域名。之前确认了 Cocos 默认加载会走下载器，但没有先验证原生 Image 路径，这是初始方案的验证缺口。

现已将微信环境改为 `wx.createImage()` → `image.src=原始URL` → `ImageAsset` → `Texture2D` → `SpriteFrame`。不替换头像域名，不新增后端代理或转存，不改头像存储契约。加载错误或 15 秒超时会清理回调并保留内置兜底；Web 继续使用原加载方式。

官方小游戏类型声明确认 `wx.createImage` 与 `Image.src/onload/onerror` 能力：[微信小游戏官方 API 类型](https://github.com/wechat-miniprogram/minigame-api-typings/blob/master/types/wx/lib.wx.api.d.ts)。本地 Cocos 3.8.8 微信适配层同样用 `wx.createImage` 构造图片对象。上述资料能够支持该接入方式，但不能替代当前账号、基础库和真机的实际加载验证。
